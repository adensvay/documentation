## 5. Root Cause Analysis

**Root Cause:** Incorrect DNS server configuration on COMP01.

The workstation was configured to query Google's public DNS server (`8.8.8.8`) instead of the domain controller (`192.168.17.128`).

Google DNS can resolve public domains such as `google.com`, but it does not contain private Active Directory DNS records for `aden.local`.

Consequently:

- External websites remained accessible.
- Direct IP connectivity to the domain controller worked.
- Internal hostname resolution failed.

### Key Troubleshooting Distinction

**IP connectivity and DNS resolution are separate.**

A workstation can successfully communicate with a server using its IP address while being unable to resolve the server's hostname.

## 6. Remediation

Performed on COMP01 using elevated PowerShell as `ADEN\svadmin`.

### Step 1 — Restore Internal DNS

```powershell
Set-DnsClientServerAddress -InterfaceAlias "Ethernet0" -ServerAddresses "192.168.17.128"
```

### Step 2 — Clear the DNS Cache

```powershell
Clear-DnsClientCache
```

Equivalent command:

```cmd
ipconfig /flushdns
```

### Step 3 — Verify DNS Configuration

```powershell
ipconfig /all
```

Confirmed:

```text
DNS Servers: 192.168.17.128
```

The final configuration uses the internal AD DNS server rather than Google's public resolver.

## 9. Real-World Enterprise Considerations

Not every DNS issue involves an incorrect DNS server address.

| Scenario | Possible Root Cause |
|---|---|
| External websites work, internal resources fail | Incorrect DNS resolver or VPN DNS settings |
| DNS queries time out | DNS server unavailable, unreachable, or blocked |
| DNS returns NXDOMAIN | Missing record, incorrect hostname, or wrong resolver |
| Multiple employees affected | Shared DNS or DHCP infrastructure problem |
| Issue returns after DHCP renewal | Incorrect DHCP DNS options |
| Only one internal hostname fails | Missing or incorrect DNS record |

In an enterprise environment, technicians should verify the approved corporate DNS baseline before modifying endpoint configuration.

### DHCP Considerations

COMP01 receives its IP configuration through VMware DHCP at `192.168.17.254`.

A future lab task is to verify whether DHCP automatically distributes the correct AD DNS server.

Manually setting DNS can remediate a local issue, but if DHCP is distributing incorrect DNS information, the underlying DHCP configuration should be corrected.

### DNS Forwarding

Domain-joined clients typically query internal DNS servers capable of resolving Active Directory records.

The internal DNS infrastructure can then resolve external domains through forwarders or recursive DNS resolution.

## 11. Lessons Learned

1. **DNS and IP connectivity are separate.** A device may reach a server by IP while failing to resolve its hostname.
2. **Public DNS cannot resolve private Active Directory namespaces.** Domain-joined clients require AD-aware DNS infrastructure.
3. **`ipconfig /all` is a foundational diagnostic tool.** It displays IP, gateway, DHCP, and DNS configuration.
4. **Compare IP connectivity with hostname resolution.** This helps distinguish network failures from DNS failures.
5. **Administrative permissions matter.** Changing DNS settings requires an appropriately elevated account.
6. **DNS issues can originate from multiple layers.** DHCP, VPN, DNS servers, firewall rules, and missing records can all contribute.
7. **Always verify after remediation.** Both internal and external DNS resolution should work.
8. **Understand where configuration originates.** DHCP-provided DNS settings and manual DNS overrides should be distinguished.
