## 1. Incident Summary

A user reported that their Windows 11 workstation suddenly lost internet connectivity while other employees remained unaffected.

**User report:**

> "My computer suddenly stopped connecting to the internet. I can't access any websites, but my coworkers aren't having problems. I've already restarted the computer."

The workstation was found to have a manually configured link-local IPv4 address, disabled DHCP, and no default gateway.

The troubleshooting exercise focused on identifying IPv4 configuration problems and restoring automatic addressing.

## 3. Fault Injection

The following PowerShell commands were used to simulate a workstation experiencing link-local IPv4 connectivity problems.

Run as Administrator:

```powershell
$adapter = "Ethernet0"

New-NetIPAddress `
    -InterfaceAlias $adapter `
    -IPAddress "169.254.77.25" `
    -PrefixLength 16
```

### Effect

The command configured a static link-local IPv4 address on the workstation.

Observed consequences included:

- DHCP disabled
- IPv4 address changed to 169.254.77.25
- Default gateway missing
- DNS resolution unavailable
- External connectivity lost

**Technical note:** This simulated APIPA-like symptoms through manual configuration. It was not a genuine DHCP lease failure or automatically assigned APIPA address.

## 4. Initial Investigation

### Step 1 — Identify User and Hostname

```powershell
whoami
hostname
```

Results:

```text
comp02\labadmin
COMP02
```

Confirmed that troubleshooting was being performed on the intended workstation.

### Step 2 — Test External IP Connectivity

```powershell
ping 8.8.8.8
```

Result:

```text
PING: transmit failed. General failure.
PING: transmit failed. General failure.
PING: transmit failed. General failure.
PING: transmit failed. General failure.

Packets: Sent = 4, Received = 0, Lost = 4 (100% loss)
```

**Interpretation:**

The workstation could not communicate with an external IPv4 address.

Because the test used an IP address rather than a hostname, DNS resolution was not required for this test.

The result suggested a broader network configuration or routing problem.

### Step 3 — Test DNS Resolution

```powershell
nslookup google.com
```

Result:

```text
Server:  UnKnown
Address: fec0:0:0:ffff::1

*** UnKnown can't find google.com: No response from server
```

**Interpretation:**

The workstation could not obtain a DNS response.

The configured DNS addresses were not providing usable name resolution.

However, because direct IP connectivity also failed, DNS alone could not explain the entire incident.

### Step 4 — Inspect Network Configuration

```powershell

```

Relevant output:


### Key Findings

1. The workstation had a link-local IPv4 address.
2. DHCP was disabled.
3. No IPv4 default gateway was configured.
4. No usable DNS server was available.
5. External IP connectivity and DNS resolution both failed.

## 5. Root Cause Analysis

**Root cause:** Incorrect static IPv4 configuration with DHCP disabled.

The workstation had been manually assigned:

```text
169.254.77.25/16
```

This address did not belong to the expected LAN subnet:

```text
192.168.254.0/24
```

The workstation also lacked a default gateway.

Without a valid route to external networks, COMP02 could not communicate with internet destinations.

### APIPA vs. Static Link-Local Address

APIPA (Automatic Private IP Addressing) is a Windows mechanism that can assign an address in the `169.254.0.0/16` range when automatic IPv4 configuration is enabled but no DHCP lease can be obtained.

In this incident, the link-local address was configured manually.

Therefore, the observed symptoms resembled APIPA, but the underlying cause was disabled DHCP and incorrect static addressing.

**Troubleshooting lesson:** A `169.254.x.x` address is a clue, not proof that the DHCP server is unavailable. Always inspect whether DHCP is enabled.

---

## 6. Resolution

### Step 1 — Re-enable DHCP

```powershell
Set-NetIPInterface `
    -InterfaceAlias "Ethernet0" `
    -AddressFamily IPv4 `
    -Dhcp Enabled
```

This restores automatic IPv4 address configuration.

### Step 2 — Remove the Incorrect Static Address

```powershell
Remove-NetIPAddress `
    -InterfaceAlias "Ethernet0" `
    -IPAddress "169.254.77.25" `
    -Confirm:$false
```

This removes the manually configured link-local IPv4 address.

### Step 3 — Restore Automatic DNS Configuration

```powershell
Set-DnsClientServerAddress `
    -InterfaceAlias "Ethernet0" `
    -ResetServerAddresses
```

This resets the adapter's DNS server configuration to automatic settings.

### Step 4 — Request a New DHCP Lease

```powershell
ipconfig /renew
```

This requests IPv4 configuration from the DHCP server.

A Windows restart or Group Policy refresh is not normally necessary for these changes.

## 9. General Troubleshooting Workflow

For future Windows connectivity incidents:

1. Confirm the affected workstation and user.
2. Determine whether the problem affects one device or multiple devices.
3. Check the network adapter's connection status.
4. Inspect the IP address, subnet mask, DHCP status, gateway, and DNS servers.
5. Ping the default gateway.
6. Ping a known external IP address.
7. Test DNS resolution separately.
8. Identify whether the failure is local addressing, routing, DNS, or an upstream network issue.
9. Apply the smallest appropriate configuration change.
10. Verify connectivity and document the resolution.

### Quick Diagnostic Sequence

```powershell
hostname
whoami

Get-NetAdapter
ipconfig /all

ping 192.168.254.254
ping 8.8.8.8

nslookup google.com
route print
```

**Note:** The gateway address is environment-specific. Replace `192.168.254.254` with the workstation's actual gateway when using this workflow elsewhere.

## 10. Lessons Learned

- A `169.254.x.x` address indicates link-local IPv4 addressing but does not, by itself, identify the root cause.
- DHCP status should be checked before assuming a DHCP server outage.
- A missing default gateway can prevent communication outside the local subnet.
- Testing an IP address separately from a hostname helps distinguish routing/connectivity problems from DNS problems.
- `ipconfig /all` provides a fast overview of critical network configuration.
- PowerShell networking cmdlets allow administrators to restore configuration without using the Windows Settings GUI.
- VMware snapshots provide useful recovery points before troubleshooting simulations.
- Network troubleshooting should proceed from local configuration toward external connectivity.
