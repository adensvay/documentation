
# INC-031 — DNS Resolution Failure on Windows 11

**Date:** October 23, 2026  
**Priority:** P3 — Medium  
**Status:** Resolved  
**Device:** COMP02  
**Operating System:** Windows 11  
**Interface:** Ethernet0  
**Category:** Networking / DNS / Endpoint Troubleshooting

---

## 1. Incident Summary

### User Report

> "My computer is connected to the network, but I can't open any websites in my browser. Everything was working yesterday, and my coworkers aren't having any problems."

### Business Impact

A single workstation was unable to access websites and web-based applications despite having a working network connection.

### Objective

- Determine whether the failure involves IP connectivity, DNS, or another network component.
- Identify the root cause.
- Restore hostname resolution without unnecessarily modifying working network settings.
- Verify connectivity after remediation.

## 3. Initial Investigation

### Step 1 — Test External IP Connectivity

Command:

    ping 8.8.8.8

Result:

    Reply from 8.8.8.8: bytes=32 time=5ms TTL=117
    Reply from 8.8.8.8: bytes=32 time=5ms TTL=117
    Reply from 8.8.8.8: bytes=32 time=4ms TTL=117
    Reply from 8.8.8.8: bytes=32 time=4ms TTL=117

    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)

**Interpretation:**

The workstation could communicate with an external IPv4 address.

This suggested that:

- The workstation had a usable IP configuration.
- Local routing and internet connectivity were functioning.
- The issue was unlikely to be a complete network outage.

**Important:** A successful ping to an IP address does not prove DNS is functioning because no hostname resolution is required.

### Step 2 — Test DNS Resolution

Command:

    nslookup google.com

Result:

    DNS request timed out.
    Server: UnKnown
    Address: 192.0.2.53

    *** Request to UnKnown timed-out

**Interpretation:**

The configured DNS server was not responding to DNS queries.

The browser was also unable to resolve website hostnames.

This narrowed the investigation toward DNS configuration or DNS server availability.

**Note:** The `Server: UnKnown` label alone does not prove a DNS failure. It can appear when the DNS server's IP address lacks a reverse DNS record. The repeated query timeouts were the meaningful failure evidence.

### Step 3 — Inspect Network Configuration

Command:

    ipconfig /all

Relevant output:

    Host Name . . . . . . . . . : COMP02
    DHCP Enabled . . . . . . . : Yes
    IPv4 Address . . . . . . . : 192.168.254.78
    Subnet Mask . . . . . . . . : 255.255.255.0
    Default Gateway . . . . . : 192.168.254.254
    DHCP Server . . . . . . . . : 192.168.254.254
    DNS Servers . . . . . . . : 192.0.2.53

**Findings:**

- DHCP was enabled.
- The workstation had a valid IPv4 address.
- A default gateway was configured.
- The DNS server was set to `192.0.2.53`.
- The configured DNS server differed from the previously working configuration.

`192.0.2.0/24` is a reserved documentation address range (TEST-NET-1), not a normal public DNS service.

### Step 4 — Confirm Configured DNS Servers

PowerShell:

    Get-DnsClientServerAddress -InterfaceAlias "Ethernet0" -AddressFamily IPv4

Result:

    InterfaceAlias  InterfaceIndex  AddressFamily  ServerAddresses
    Ethernet0       4               IPv4           {192.0.2.53}

**Interpretation:**

The network adapter was configured to use the incorrect DNS server.

### Step 5 — Test an Alternative DNS Server

Command:

    nslookup google.com 192.168.254.254

Result:

    Server: gateway.home
    Address: 192.168.254.254

    Non-authoritative answer:
    Name: google.com
    Addresses:
      2607:f8b0:4007:803::200e
      142.251.214.110

**Interpretation:**

The gateway's DNS service successfully resolved `google.com`.

This demonstrated that:

1. DNS queries could reach a functioning resolver.
2. The original DNS server configuration was the likely root cause.
3. The workstation's IPv4 address and default gateway did not need modification.

## 4. Root Cause

**Incorrect DNS server configuration on the Windows 11 network adapter.**

COMP02 was configured to send DNS queries to:

    192.0.2.53

This server did not respond to the workstation's DNS queries.

As a result, applications relying on hostname resolution could not locate websites, even though external IP connectivity remained functional.

### Why DHCP Was Not the Problem

DHCP was enabled and had successfully assigned the workstation an IPv4 address.

However, Windows can use DHCP for IP addressing while retaining manually configured DNS server settings.

Therefore:

**DHCP enabled does not necessarily mean DNS server addresses are automatically assigned.**

---

## 5. Remediation

### Initial Attempt — Permission Error

Command:

    Set-DnsClientServerAddress `
        -InterfaceAlias "Ethernet0" `
        -ResetServerAddresses

Error:

    PermissionDenied
    Access to a CIM resource was not available to the client.

**Cause:**

The command was attempted without sufficient administrative privileges.

### Resolution — Elevated PowerShell

Opened PowerShell with administrator privileges and executed:

    Set-DnsClientServerAddress `
        -InterfaceAlias "Ethernet0" `
        -ResetServerAddresses

**What the command does:**

- Removes manually configured DNS server addresses from the specified interface.
- Restores automatic DNS server assignment.
- Allows Windows to use DNS server information supplied through DHCP.

**What the command does not do:**

- Change the workstation's IPv4 address.
- Change the subnet mask.
- Change the default gateway.
- Disable DHCP.
- Restart the network adapter.

This was preferable to changing unrelated, already functional network settings.

## 7. Reusable DNS Troubleshooting Commands

### A. Basic Connectivity

Check local IP configuration:

    ipconfig

View detailed network configuration:

    ipconfig /all

Test the default gateway:

    ping 192.168.254.254

Test external IPv4 connectivity without DNS:

    ping 8.8.8.8

Test connectivity using a hostname:

    ping google.com

**Interpretation:**

- IP ping works, hostname lookup fails: investigate DNS.
- Gateway ping fails: investigate local network connectivity, addressing, and firewall behavior.
- Gateway works, external IP fails: investigate routing, upstream connectivity, and filtering.
- DNS resolves but website fails: investigate TCP connectivity, browser, proxy, TLS, or application issues.

Remember that ICMP may be blocked even when other traffic works.

### B. DNS Resolution Tests

Query the configured DNS server:

    nslookup google.com

Query a specific DNS server:

    nslookup google.com 192.168.254.254

Query a public DNS resolver:

    nslookup google.com 1.1.1.1

PowerShell DNS query:

    Resolve-DnsName google.com

Query a specific DNS server with PowerShell:

    Resolve-DnsName google.com -Server 192.168.254.254

Query an A record:

    Resolve-DnsName google.com -Type A

Query an MX record:

    Resolve-DnsName google.com -Type MX

**Interpretation:**

If the default DNS server times out but an alternative resolver works, investigate the configured DNS server, its reachability, and adapter DNS settings.

### C. Inspect DNS Configuration

View DNS servers on all adapters:

    Get-DnsClientServerAddress

View IPv4 DNS servers for Ethernet0:

    Get-DnsClientServerAddress `
        -InterfaceAlias "Ethernet0" `
        -AddressFamily IPv4

Inspect the adapter's IP configuration:

    Get-NetIPConfiguration -InterfaceAlias "Ethernet0"

Inspect IPv4 DHCP status:

    Get-NetIPInterface `
        -InterfaceAlias "Ethernet0" `
        -AddressFamily IPv4

### D. Repair DNS Configuration

**Run configuration changes in elevated PowerShell.**

Restore automatic DNS assignment:

    Set-DnsClientServerAddress `
        -InterfaceAlias "Ethernet0" `
        -ResetServerAddresses

Manually assign a DNS server when appropriate:

    Set-DnsClientServerAddress `
        -InterfaceAlias "Ethernet0" `
        -ServerAddresses "192.168.254.254"

Assign primary and secondary DNS servers:

    Set-DnsClientServerAddress `
        -InterfaceAlias "Ethernet0" `
        -ServerAddresses @("192.168.254.254", "1.1.1.1")

**Caution:** Do not indiscriminately assign public DNS servers to domain-joined computers. Active Directory clients typically require DNS servers capable of resolving internal AD records. Public DNS can break domain controller discovery and authentication.

### E. DNS Cache Troubleshooting

Display cached DNS records:

    ipconfig /displaydns

Clear the local DNS resolver cache:

    ipconfig /flushdns

PowerShell equivalent:

    Clear-DnsClientCache

**Important:** Clearing the DNS cache does not repair an incorrect DNS server configuration. Use it when cached records may be stale or incorrect.

### F. DHCP Troubleshooting

Release DHCP-assigned IPv4 configuration:

    ipconfig /release

Request a new DHCP lease:

    ipconfig /renew

**Caution:** These commands can temporarily disconnect the workstation. They are not required for every DNS issue and may interrupt remote support sessions.

### G. TCP Connectivity

Test whether HTTPS is reachable:

    Test-NetConnection google.com -Port 443

Test connectivity to a DNS server over TCP port 53:

    Test-NetConnection 192.168.254.254 -Port 53

**Important:** Most conventional DNS queries use UDP port 53. A successful TCP port 53 test does not prove UDP DNS queries are working, and a failed TCP test does not always mean DNS is unavailable.

## 9. Key Lessons Learned

### 1. IP Connectivity and DNS Are Separate

A workstation can successfully reach an external IP address while being unable to access websites by hostname.

### 2. Always Inspect the DNS Server Address

The `DNS Servers` field in `ipconfig /all` is a critical diagnostic clue when hostname resolution fails.

### 3. DHCP and DNS Are Related but Distinct

DHCP may provide DNS server addresses, but Windows can also retain manually configured DNS settings.

### 4. Test Before Changing Configuration

Using:

    nslookup google.com 192.168.254.254

confirmed that an alternative resolver worked before any remediation was attempted.

### 5. Use Administrative Privileges for Configuration Changes

Read-only diagnostics may work in standard PowerShell, but modifying network settings generally requires elevation.

### 6. Avoid Unnecessary Network Changes

The workstation's IPv4 address, gateway, and DHCP configuration were already functional. Changing them would have introduced unnecessary risk.

### 7. DNS Cache Flushing Is Not a Universal Fix

If the configured DNS server is unreachable or incorrect, flushing cached records will not correct the underlying issue.

## 11. Personal Troubleshooting Checklist

When a Windows user reports that websites do not load:

- [ ] Identify whether the issue affects one device or multiple users.
- [ ] Run `ipconfig /all`.
- [ ] Check IPv4 address, subnet mask, and gateway.
- [ ] Check DHCP status and DNS server addresses.
- [ ] Test the default gateway.
- [ ] Test external IP connectivity.
- [ ] Run `nslookup` against the configured DNS server.
- [ ] Query a known working DNS server directly.
- [ ] Determine whether DNS is manually or automatically configured.
- [ ] Correct the configuration with administrator privileges.
- [ ] Verify DNS resolution.
- [ ] Verify actual website access.
- [ ] Document root cause, commands, and resolution.

## 12. Final Takeaway

**Symptom:** Websites failed to load, but external IP connectivity worked.

**Root Cause:** Incorrect DNS server (`192.0.2.53`) configured on Ethernet0.

**Resolution:** Restored automatic DNS server assignment using `Set-DnsClientServerAddress -ResetServerAddresses`.

**Verification:** `nslookup google.com` succeeded using `192.168.254.254`, and external IP connectivity remained functional.

**Core troubleshooting principle:**

> When an IP address is reachable but hostnames fail, investigate DNS configuration and resolution before changing IP addressing or routing.
