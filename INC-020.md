
# INC-020 — Internal Website Unreachable Due to Outbound Firewall Rule

**Category:** Endpoint Support / Network Connectivity  
**Priority:** P3 — Standard  
**Environment:** Windows 11 Enterprise, Windows Server 2022, Active Directory, IIS, PowerShell  
**Affected Device:** COMP01  
**Reported User:** Rachel Brooks  
**Domain:** aden.local  
**Date:** October 16, 2026  
**Status:** Remediated — final browser verification pending

---

## 1. Incident Summary

A user reported being unable to access an internal work portal from their Windows 11 workstation, although other websites remained accessible.

Initial network diagnostics confirmed that the portal hostname resolved to the correct IP address and that the server responded to ICMP ping requests. However, COMP01 could not establish a TCP connection to the web server on port 80.

Further investigation revealed an enabled outbound Windows Firewall rule blocking TCP traffic from COMP01 to the internal web server.

The rule was removed, and TCP connectivity was successfully restored.

**Root Cause:** Client-side Windows Defender Firewall outbound block rule.

**Resolution:** Removed the targeted firewall rule and verified TCP port 80 connectivity.

## 4. Troubleshooting Process

### Step 1 — Verify DNS Resolution

On COMP01:

```powershell
Resolve-DnsName portal.aden.local
```

**Observed output:**

```text
Name                Type    IPAddress
----                ----    ---------
portal.aden.local   A       192.168.17.128
```

**Result:** PASS

**Interpretation:**

DNS returned the expected IP address of the domain controller.

This reduced the likelihood of a DNS record or name-resolution issue.

However, successful DNS resolution alone does not guarantee application connectivity.

### Step 2 — Test HTTP Connectivity

On COMP01:

```powershell
Test-NetConnection portal.aden.local -Port 80
```

**Observed output:**

```text
RemoteAddress     : 192.168.17.128
RemotePort        : 80
SourceAddress     : 192.168.17.129
PingSucceeded     : True
TcpTestSucceeded  : False
```

**Result:** FAIL

**Interpretation:**

The server responded to ICMP ping requests, but COMP01 could not establish a TCP connection to port 80.

This suggested a transport-layer or network-filtering problem.

Possible causes included:

- Client-side outbound firewall restrictions
- Server-side inbound firewall restrictions
- Network access controls
- Web service not listening on the required port

**Key finding:** ICMP connectivity does not guarantee TCP connectivity.

### Step 3 — Verify Web Server Availability

On the domain controller:

```powershell
Test-NetConnection 127.0.0.1 -Port 80
```

**Observed output:**

```text
RemoteAddress     : 127.0.0.1
RemotePort        : 80
TcpTestSucceeded  : True
```

**Result:** PASS

**Interpretation:**

The web server was accepting TCP connections locally on port 80.

This demonstrated that an HTTP listener was running on the server.

It did not independently prove that all remote clients could reach the server, but it reduced the likelihood of a stopped web service.

### Step 4 — Inspect Client Outbound Firewall Rules

On COMP01:

```powershell
Get-NetFirewallRule -Direction Outbound -Enabled True -Action Block |
    Select-Object DisplayName, Direction, Action, Enabled
```

**Observed output:**

```text
DisplayName         : Lab-INC020-Endpoint
Direction           : Outbound
Action              : Block
Enabled             : True
```

**Result:** Suspicious firewall rule identified.

The rule was enabled and configured to block outbound traffic.

Additional inspection was required to determine whether it matched the failed connection.

### Step 5 — Inspect Firewall Port Filters

```powershell
Get-NetFirewallRule -DisplayName "Lab-INC020-Endpoint" |
    Get-NetFirewallPortFilter |
    Format-List Protocol, LocalPort, RemotePort
```

**Observed output:**

```text
Protocol    : TCP
LocalPort   : Any
RemotePort  : 80
```

**Interpretation:**

The rule blocked outbound TCP traffic targeting remote port 80.

This matched the failed HTTP connection.

### Step 6 — Inspect Firewall Address Filters

```powershell
Get-NetFirewallRule -DisplayName "Lab-INC020-Endpoint" |
    Get-NetFirewallAddressFilter |
    Format-List LocalAddress, RemoteAddress
```

**Observed output:**

```text
LocalAddress   : Any
RemoteAddress  : 192.168.17.128
```

**Interpretation:**

The rule specifically targeted the internal web server's IP address.

Combining the firewall rule properties established that the rule blocked:

**Outbound TCP traffic from COMP01 to 192.168.17.128 on remote port 80.**

This precisely matched the failed connection test.

## 5. Root Cause Analysis

The root cause was an enabled outbound Windows Firewall rule named:

```text
Lab-INC020-Endpoint
```

The rule matched the following traffic:

| Property | Value |
|---|---|
| Direction | Outbound |
| Action | Block |
| Enabled | True |
| Protocol | TCP |
| Local Port | Any |
| Remote Port | 80 |
| Local Address | Any |
| Remote Address | 192.168.17.128 |

### Why DNS and Ping Still Worked

The firewall rule blocked TCP traffic to a specific destination and port.

DNS queries and ICMP ping requests use different protocols and traffic paths.

Consequently:

- DNS could resolve the correct server address.
- ICMP ping could succeed.
- TCP port 80 could still be blocked.
- The HTTP website could remain inaccessible.

The failure was therefore not caused by incorrect DNS resolution or a general loss of IP connectivity.

## 6. Remediation

Because this was a deliberately injected lab rule, the targeted firewall rule could be safely removed.

On COMP01:

```powershell
Remove-NetFirewallRule -DisplayName "Lab-INC020-Endpoint"
```

The command completed without error.

**Note:** An initial attempt contained a typo in the cmdlet name and returned `CommandNotFoundException`. After correcting the spelling, the command executed successfully.

In production, a technician should verify the purpose and ownership of a firewall rule before disabling or removing it.

## 9. Additional Security Observation — Microsoft Defender

An earlier attempt to stage INC-020 modified the Windows hosts file.

Microsoft Defender detected:

```text
SettingsModifier:Win32/HostsFileHijack
```

**Affected file:**

```text
C:\Windows\System32\drivers\etc\hosts
```

Defender quarantined the suspicious modification.

Subsequent inspection showed that the hosts file contained standard localhost entries and that DNS resolution for the internal portal remained correct.

### Commands Used

Inspect the hosts file:

```powershell
Get-Content "$env:SystemRoot\System32\drivers\etc\hosts"
```

Query the DNS record:

```powershell
Resolve-DnsName portal.aden.local
```

**Security lesson:**

Endpoint protection can detect and remediate suspicious configuration changes automatically.

A script reporting successful execution does not guarantee that its changes remain active afterward.

The quarantined hosts-file injection was not treated as the resolved fault for this ticket.

The completed troubleshooting exercise used the replacement outbound firewall rule.

## 10. HTTP vs. HTTPS Troubleshooting

During investigation, HTTPS connectivity was also tested:

```powershell
Test-NetConnection portal.aden.local -Port 443
```

The test failed from both COMP01 and the DC.

On the DC:

```powershell
Get-NetTCPConnection -LocalPort 443 -State Listen -ErrorAction SilentlyContinue
```

No listener was returned.

This indicated that the server was not listening on TCP port 443.

Because the lab portal was configured to serve HTTP on port 80, the HTTPS failure was not evidence of the injected client-side fault.

**Lesson:** Always verify which protocol and port the application is expected to use before interpreting a failed connection test.

## 11. Troubleshooting Framework

For future website connectivity incidents:

1. **Confirm the exact URL and error.** Determine whether the user is accessing HTTP or HTTPS.
2. **Check DNS.** Confirm the hostname resolves to the expected IP address.
3. **Test TCP connectivity.** Use the application's required port.
4. **Compare with a known-good system.** Determine whether the issue is client-specific.
5. **Verify the server-side listener.** Confirm the service is running and accepting connections.
6. **Inspect firewall rules.** Examine direction, action, protocol, port, and address filters.
7. **Apply the smallest authorized fix.** Avoid disabling the entire firewall.
8. **Retest the original failure.** Confirm the connection works.
9. **Document the root cause and evidence.** Record what changed and why.

## 12. Lessons Learned

### Networking

- DNS resolution does not guarantee application connectivity.
- ICMP ping does not prove TCP port availability.
- A firewall can block a particular port while permitting other network traffic.
- Client and server tests help isolate the scope of a problem.
- A failed HTTPS test may be expected when a server only provides HTTP.

### Windows Administration

- Windows Firewall rules contain separate protocol, port, and address filters.
- `Get-NetFirewallRule` alone may not display every condition necessary to understand a rule.
- Targeted firewall changes are preferable to disabling the firewall entirely.
- PowerShell Remoting enables remote endpoint diagnostics and remediation.

### Security

- Defender may automatically quarantine suspicious system changes.
- A successful injection does not necessarily mean the intended fault persists.
- Security detections should be investigated rather than ignored or bypassed.

### Professional Practice

- Begin with the user's reported symptoms.
- Form hypotheses from diagnostic evidence.
- Confirm the cause before making configuration changes.
- Verify the result using the same test that originally failed.
- Maintain reusable command references rather than relying solely on memorization.
