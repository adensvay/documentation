## 2. Initial Assessment

Before provisioning, the intended employee identity was reviewed to avoid conflicts with existing accounts.

An existing user named Daniel Kim was present in the environment, but this was a different employee from Daniel Park.

A previous proposed employee, Maya Chen, already existed as a cloud identity, so the onboarding scenario was changed to Daniel Park to avoid introducing an unintended hybrid identity-matching exercise.

The lab also contained a cloud-only Sales group in Entra ID. To avoid confusing this group with a newly synchronized on-premises group, a distinct on-premises group named `AD-Local-Sales` was used.

### Important Identity Distinction

- The on-premises AD domain is `aden.local`.
- The preferred hybrid user UPN suffix is `adensvaygmail.onmicrosoft.com`.
- The legacy Windows sign-in format is `ADEN\dpark`.
- An account with an `@aden.local` UPN can still synchronize to Entra ID.
- Synchronization alone does not grant Microsoft 365 licenses or application access.

## 3. Actions Performed

### Step 1 — Created the User in Active Directory

Used Active Directory Users and Computers (ADUC) to create the new employee account.

The account was placed in:

`OU=Users,OU=USA,DC=aden,DC=local`

Configured the following information:

- First name: Daniel
- Last name: Park
- Username: `dpark`
- Department: Sales
- Job title: Sales Representative
- Manager: Rachel Brooks

The account was enabled.

### Step 2 — Configured Departmental Group Membership

Used ADUC to add Daniel Park to the on-premises security group:

`AD-Local-Sales`

Verified through the group's **Members** tab that Daniel Park appeared as a member.

**Important:** Membership in a security group does not automatically grant access to a resource. Permissions, application assignments, or policies must explicitly reference that group.

The existing Entra cloud-only Sales group remains a separate object with separate membership.

### Step 3 — Verified Entra ID Synchronization

Opened the Microsoft Entra admin center and located Daniel Park in the Users directory.

Observed that the new identity appeared in Entra ID and was reported as synchronized from on-premises Active Directory.

This confirmed that the new AD user was within the configured synchronization scope and that identity synchronization was functioning.

### Step 4 — Audited AD Attributes with PowerShell

Ran the following command on the domain controller:

```powershell
Get-ADUser dpark -Properties `
    UserPrincipalName,Department,Title,Manager,EmployeeID,Enabled,PasswordLastSet,PasswordNeverExpires |
    Select-Object Name,SamAccountName,UserPrincipalName,
        Department,Title,Manager,EmployeeID,Enabled,
        PasswordLastSet,PasswordNeverExpires
```

Initial results:

```text
Name                 : Daniel Park
SamAccountName       : dpark
UserPrincipalName    : dpark@aden.local
Department           : Sales
Title                : Sales Representative
Manager              : CN=Rachel Brooks,OU=Users,OU=USA,DC=aden,DC=local
EmployeeID           :
Enabled              : True
PasswordLastSet      : 10/20/2026 12:37:07 PM
PasswordNeverExpires : False
```

### Findings

The audit identified two incomplete attributes:

1. The user principal name used the internal `aden.local` suffix.
2. The employee ID was blank.

The department, job title, manager, and account-enabled status were correct.

This demonstrated the value of validating onboarding attributes after GUI-based account creation.

### Step 5 — Corrected Missing Attributes

Used PowerShell to update Daniel's UPN and employee ID:

```powershell
Set-ADUser -Identity dpark `
    -UserPrincipalName "dpark@adensvaygmail.onmicrosoft.com" `
    -EmployeeID "EMP-1044"
```

Verified the attributes with:

```powershell
Get-ADUser dpark -Properties UserPrincipalName,EmployeeID |
    Select-Object Name,UserPrincipalName,EmployeeID
```

The attribute corrections were reported as completed successfully.

A separate post-change command output was not captured in this report.

## 6. PowerShell Reference — Future Onboarding

The following commands are **reference examples**, not all commands executed during INC-024.

### Check Whether a Username Already Exists

```powershell

```

### Check Whether an Employee ID Already Exists

```powershell

    -Properties EmployeeID
```

### Check for an Existing UPN

```powershell

```

Cloud identity conflicts must also be checked separately in Entra ID.

### Inspect an Existing Employee

```powershell
Get-ADUser rbrooks -Properties `
    Department,Title,Manager,MemberOf |
    Select-Object Name,Department,Title,Manager,MemberOf
```

### Create a New AD User

Example only. Validate the target OU and HR-approved attributes before use.

```powershell
New-ADUser `
    -Name "Daniel Park" `
    -GivenName "Daniel" `
    -Surname "Park" `
    -SamAccountName "dpark" `
    -UserPrincipalName "dpark@adensvaygmail.onmicrosoft.com" `
    -Path "OU=Users,OU=USA,DC=aden,DC=local" `
    -Department "Sales" `
    -Title "Sales Representative" `
    -EmployeeID "EMP-1044" `
    -Enabled $false
```

This creates a disabled account without configuring a password. Password setup and approved activation are separate steps.

### Assign a Manager

```powershell
Set-ADUser dpark -Manager "rbrooks"
```

### Add a User to an Approved Security Group

```powershell
Add-ADGroupMember `
    -Identity "AD-Local-Sales" `
    -Members "dpark"
```

### Verify Group Membership

```powershell
Get-ADPrincipalGroupMembership dpark |
    Select-Object Name,GroupCategory,GroupScope
```

### Configure First-Login Password Change

After securely setting an initial password, and where supported by the organization's authentication configuration:

```powershell
Set-ADUser dpark -ChangePasswordAtLogon $true
```

The initial password must be delivered through an approved secure channel.

### Enable the Account When Authorized

```powershell

```

### Trigger Entra Connect Delta Synchronization

Run on the server hosting the Entra Connect synchronization engine:

```powershell
Start-ADSyncSyncCycle -PolicyType Delta
```

A scheduled synchronization may make a manual sync unnecessary.

### Verify Key Onboarding Attributes

## 7. Troubleshooting and Operational Lessons

### On-Premises AD vs. Entra ID

For a hybrid identity environment, on-premises AD is generally the authoritative source for synchronized user attributes.

The standard workflow is:

1. Receive an approved HR onboarding request.
2. Check for existing identities and naming conflicts.
3. Create the on-premises AD account.
4. Configure user attributes and approved group memberships.
5. Synchronize the identity to Entra ID.
6. Verify the correct cloud identity.
7. Assign required Microsoft 365 licenses and cloud access.
8. Validate first-login requirements and application access.
9. Document completion and securely hand off credentials.

### UPN vs. AD Domain

The AD domain name and the user principal name suffix do not have to be identical.

In this lab:

```text
AD Domain:         aden.local
Windows Logon:     ADEN\dpark
Hybrid User UPN:   dpark@adensvaygmail.onmicrosoft.com
```

Using a verified cloud UPN suffix helps maintain consistent usernames across AD and Microsoft 365.

### Security Groups

Departmental group membership should be assigned according to approved role-based access requirements.

A synchronized on-premises group and an existing cloud-only Entra group are not automatically merged, even if they share the same display name.

### Identity Provisioning vs. Full Onboarding

A synchronized user account is not necessarily a fully onboarded employee.

Additional work may include:

- Microsoft 365 license assignment
- MFA registration
- Application and resource permissions
- Device enrollment and provisioning
- First-login verification
- Secure credential handoff

## 10. Reflection

This incident demonstrated that creating an AD account is only the first stage of enterprise onboarding.

The user was successfully created through ADUC and appeared in Microsoft Entra ID, but a subsequent PowerShell audit revealed that the UPN and employee ID were incomplete.

Correcting those attributes reinforced the importance of validating account properties rather than assuming a successful GUI operation means the onboarding process is finished.

For future incidents, I want to become comfortable performing the same workflow through PowerShell, including input validation, duplicate detection, group assignment, logging, and post-provisioning verification.

**Primary takeaway:** A successful onboarding workflow must verify identity, access, security, and readiness—not merely account existence.
