
# Ticket #15 — DNS Name Resolution and TCP Connectivity Troubleshooting

**Incident ID:** INC-015  
**Date:** October 14, 2026  
**Status:** DNS investigation completed; end-to-end SMB access not validated  
**Category:** Networking / DNS / Windows Server  
**Difficulty:** L1–L2  
**Environment:** Windows Server 2022, Windows 11, Active Directory DNS  
**Domain:** `aden.local`

## 1. Objective

Investigate an internal hostname that resolves to an unexpected IP address and determine whether the connectivity failure originates from DNS, the network, or the destination service.

This exercise focused on:

- Inspecting client IP configuration
- Understanding DNS zones and A records
- Testing DNS name resolution
- Testing TCP connectivity to specific ports
- Identifying incorrect DNS records
- Correcting DNS configuration
- Verifying changes from the client

## 2. Lab Environment

| Component | Hostname | IP Address |
|---|---|---|
| Domain Controller / DNS Server | `WIN-8QGPUAN7QO8` | `192.168.17.128` |
| Windows 11 Client | `COMP01` | `192.168.17.129` |
| Default Gateway | VMware network gateway | `192.168.17.2` |
| DHCP Server | VMware DHCP service | `192.168.17.254` |
| Simulated Internal Resource | `deptfiles.aden.local` | Initially `203.0.113.77` |

The simulated internal resource was represented by a DNS record. No dedicated SMB file server was provisioned for this exercise.

## 3. Initial Symptoms

A client was unable to reach an internal resource identified by:

`deptfiles.aden.local`

The client maintained general network connectivity and could access other services.

The initial troubleshooting objective was to determine whether the problem involved:

1. Client network configuration
2. DNS name resolution
3. Network connectivity
4. Destination service availability

## 4. Investigation

### Step 1 — Inspect Client Network Configuration

Executed on COMP01:

```powershell
ipconfig /all
```

Relevant findings:

```text
IPv4 Address    : 192.168.17.129
Subnet Mask     : 255.255.255.0
Default Gateway : 192.168.17.2
DHCP Server     : 192.168.17.254
DNS Server      : 192.168.17.128
```

**Interpretation:**

- COMP01 had an IPv4 address on the local subnet.
- A default gateway was configured.
- The client was configured to use the domain controller for DNS.
- DHCP was enabled.

This provided a baseline for investigating connectivity and name resolution.

### Step 2 — Test DNS Name Resolution

Executed:

```powershell
nslookup deptfiles.aden.local
```

Result:

```text
Address: 203.0.113.77
```

Verified using PowerShell:

```powershell
Resolve-DnsName deptfiles.aden.local
```

Result:

```text
Name                 Type TTL Section IPAddress
----                 ---- --- ------- ---------
deptfiles.aden.local A    300 Answer  203.0.113.77
```

**Interpretation:**

DNS successfully resolved the hostname, but the returned address was unexpected.

`203.0.113.0/24` is the TEST-NET-3 IPv4 range reserved for documentation and examples.

A successful DNS lookup only confirms that a DNS answer was returned. It does not establish whether the destination is correct, reachable, or hosting the requested service.

### Step 3 — Test TCP Connectivity

Tested SMB connectivity to the resolved hostname:

```powershell
Test-NetConnection deptfiles.aden.local -Port 445
```

Result:

```text
ComputerName     : deptfiles.aden.local
RemoteAddress    : 203.0.113.77
RemotePort       : 445
PingSucceeded    : False
TcpTestSucceeded : False
```

**Interpretation:**

- DNS resolved the hostname.
- ICMP echo did not receive a successful response.
- TCP connection establishment to port 445 failed.
- The result did not, by itself, establish whether the cause was an incorrect address, firewall filtering, routing, or an unavailable SMB service.

Port 445 is commonly used for SMB file sharing.

### Step 4 — Test Connectivity to the DNS Server

Executed:

```powershell
Test-NetConnection 192.168.17.128 -Port 53
```

Result:

```text
ComputerName     : 192.168.17.128
RemotePort       : 53
TcpTestSucceeded : True
```

**Interpretation:**

COMP01 successfully established TCP connectivity to port 53 on the domain controller.

This confirmed that the DNS server's TCP port was reachable. It did not independently verify UDP DNS operation or the correctness of individual DNS records.

### Step 5 — Inspect Authoritative DNS Records

Opened DNS Manager on Windows Server 2022:

**Server Manager → Tools → DNS → Forward Lookup Zones → aden.local**

Identified the following A records:

| Hostname | Type | IP Address |
|---|---|---|
| `WIN-8QGPUAN7QO8` | A | `192.168.17.128` |
| `COMP01` | A | `192.168.17.129` |
| `deptfiles` | A | `203.0.113.77` |

The DNS Manager record matched the IP address returned by the client.

This narrowed the investigation to the authoritative DNS configuration rather than an unexplained client-side address.

#### DNS PowerShell Inspection

Equivalent read-only command:

```powershell
Get-DnsServerResourceRecord `
    -ZoneName "aden.local" `
    -Name "deptfiles" `
    -RRType A |
    Format-List HostName,RecordType,RecordData,TimeToLive
```

This command retrieves the configured DNS A record and its properties.

## 5. DNS Configuration and Verification

For the DNS-only exercise, the simulated hostname was temporarily pointed to the lab domain controller at `192.168.17.128`.

This was a controlled name-resolution target, not confirmation that a file server or SMB share existed on the DC.

### Update Through DNS Manager

1. Open **DNS Manager**.
2. Navigate to **Forward Lookup Zones → aden.local**.
3. Open the `deptfiles` A record.
4. Change the IPv4 address to `192.168.17.128`.
5. Save the record.

**Production consideration:** DNS records must point to the verified IP address of the actual service host. A domain controller should not be selected as a replacement file server simply because it is reachable.

### Flush Client DNS Cache

Executed on COMP01:

```powershell
ipconfig /flushdns
```

Output:

```text
Successfully flushed the DNS Resolver Cache.
```

This clears the Windows DNS client resolver cache so subsequent lookups can retrieve updated DNS information.

### Verify Updated Name Resolution

Executed:

```powershell
Resolve-DnsName deptfiles.aden.local
```

Result:

```text
Name                 Type TTL Section IPAddress
----                 ---- --- ------- ---------
deptfiles.aden.local A    300 Answer  192.168.17.128
```

**Result:** DNS name resolution was successfully updated and verified from COMP01.

**Limitation:** No actual SMB file share was configured behind `deptfiles.aden.local`. Therefore, restored file access could not be validated. DNS resolution was the only confirmed successful remediation outcome.

## 6. PowerShell and Networking Command Reference

### View all client network settings

```powershell
ipconfig /all
```

Useful for checking IPv4 addresses, subnet masks, default gateways, DHCP servers, and DNS servers.

### Query DNS using nslookup

```powershell
nslookup deptfiles.aden.local
```

Useful for quickly identifying which IP address a hostname resolves to.

### Query DNS using PowerShell

```powershell
Resolve-DnsName deptfiles.aden.local
```

Provides structured DNS response information, including record type, TTL, and returned address.

### Query a specific DNS server

```powershell
Resolve-DnsName deptfiles.aden.local -Server 192.168.17.128
```

Useful for comparing answers from a particular DNS server.

### Test TCP connectivity to an SMB server

```powershell
Test-NetConnection deptfiles.aden.local -Port 445
```

Tests whether a TCP connection can be established to the destination's SMB port.

### Test TCP connectivity to a DNS server

```powershell
Test-NetConnection 192.168.17.128 -Port 53
```

Checks TCP connectivity to DNS port 53. This does not test UDP port 53.

### Display more detailed network diagnostics

```powershell
Test-NetConnection deptfiles.aden.local -Port 445 -InformationLevel Detailed
```

Provides additional information about the network interface, source address, destination, and connection test.

### Flush the local DNS resolver cache

```powershell
ipconfig /flushdns
```

Useful after DNS changes when the client may have cached an outdated response.

### Inspect the local DNS cache

```powershell
Get-DnsClientCache
```

Displays cached DNS client entries.

### Query an authoritative DNS record

Run on a machine with the DNS Server PowerShell module and appropriate permissions:

```powershell
Get-DnsServerResourceRecord -ZoneName "aden.local" -Name "deptfiles" -RRType A
```

### Inspect all A records in a DNS zone

```powershell
Get-DnsServerResourceRecord -ZoneName "aden.local" -RRType A
```

Useful for examining host-to-IP mappings in a Windows DNS zone.

### Remove the temporary lab record

After completing the exercise, preview the removal:

```powershell
Remove-DnsServerResourceRecord `
    -ZoneName "aden.local" `
    -Name "deptfiles" `
    -RRType A `
    -RecordData "192.168.17.128" `
    -WhatIf
```

After confirming the correct target, repeat without `-WhatIf` to remove the temporary record.

This restores the DNS-only lab to its original state, assuming the record was absent before the exercise.

## 7. Networking Concepts Learned

### DNS A Records

An A record maps a hostname to an IPv4 address.

Example:

```text
comp01.aden.local → 192.168.17.129
```

DNS provides a destination address; it does not guarantee that the destination is reachable or that a particular application is running.

### Forward Lookup Zones

A forward lookup zone stores DNS records used to translate names into addresses.

The `aden.local` zone contains records associated with the Active Directory domain.

### Active Directory DNS Zones

Two important zones observed:

- `aden.local` — primary domain DNS records
- `_msdcs.aden.local` — records supporting domain controller and Active Directory service discovery

The `_msdcs` zone is an expected part of an AD DNS environment and should not be removed.

### Private IPv4 Addressing

The `192.168.17.0/24` subnet is part of the RFC 1918 private address space.

These addresses are used internally and are not directly routed across the public internet.

### TCP Three-Way Handshake

`Test-NetConnection -Port` attempts a TCP connection to the specified destination and port.

A successful TCP connection normally involves:

1. SYN — Client requests a connection.
2. SYN-ACK — Server acknowledges and responds.
3. ACK — Client acknowledges, establishing the connection.

A successful TCP test confirms connection establishment, not full application functionality.

### DNS vs. Network vs. Application

These are separate troubleshooting layers:

| Layer | Diagnostic Question | Example Tool |
|---|---|---|
| Client configuration | Does the client have appropriate network settings? | `ipconfig /all` |
| Name resolution | Does the hostname resolve correctly? | `nslookup`, `Resolve-DnsName` |
| TCP connectivity | Can the destination port be reached? | `Test-NetConnection` |
| Application | Is the required service actually working? | SMB share access test |

### DNS TTL

TTL (Time to Live) indicates how long a DNS response may be cached.

The observed TTL was 300 seconds, equivalent to five minutes.

After changing a DNS record, a client may temporarily retain an older cached response until it expires or the cache is cleared.

## 8. Key Takeaways

- Start troubleshooting at the affected client before changing server configuration.
- Inspect network settings before assuming DNS is the cause.
- Successful DNS resolution does not prove the returned address is correct.
- Use `Test-NetConnection` to distinguish DNS lookup success from TCP connectivity.
- A failed port test does not identify the root cause by itself.
- Inspect authoritative DNS records to verify the source of an unexpected DNS answer.
- Confirm the correct destination IP through an inventory or authoritative source before changing DNS.
- Flush DNS caches when appropriate and verify the updated answer.
- Do not confuse restoring DNS resolution with restoring the underlying application or file service.
- Document precisely what was tested and verified.
