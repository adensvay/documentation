# Ticket #14 — Active Directory Workstation Logon Restriction

**Incident ID:** INC-014  
**Date:** October 14, 2026  
**Status:** Resolved  
**Priority:** P3 — Single-user incident  
**Environment:** Windows Server 2022, Active Directory Domain Services, Windows 11  
**Domain:** `aden.local`  
**Affected User:** John Smith (`jsmith`)  
**Affected Workstation:** `COMP01`

## 1. Incident Summary

John Smith reported being unable to sign into his domain-joined Windows workstation, COMP01, despite using his usual credentials. He had successfully signed in previously.

**Reported Windows error:**

> Your account is configured to prevent you from using this PC. Please try another PC.

The incident was reproduced through a controlled Active Directory fault injection in a personal enterprise IT homelab.

## 2. Investigation

### Initial Triage

- Confirmed that the problem involved Windows domain sign-in.
- Collected the exact error message and identified the affected workstation.
- Located John's account in Active Directory Users and Computers (ADUC).
- Reviewed the account's workstation logon restrictions under **Account → Log On To**.

### Findings

The account was configured to permit sign-in only from the domain controller:

`WIN-8QGPUAN7QO8`

The affected workstation, `COMP01`, was absent from the permitted workstation list.

This restriction prevented John from signing into his assigned workstation.

### PowerShell Verification

The following read-only command checks the user's permitted logon workstations:

```powershell
Get-ADUser -Identity "jsmith" -Properties LogonWorkstations |
    Select-Object Name, LogonWorkstations
```

The initial output confirmed that only the domain controller was listed.

## 3. Root Cause

The Active Directory `LogonWorkstations` attribute was misconfigured, restricting John's permitted logon computers to the domain controller rather than his assigned workstation.

This was an account-level authentication restriction, not a password, DNS, or Entra ID synchronization problem.

## 4. Resolution

After confirming that John was authorized to access COMP01, the permitted workstation list was updated using ADUC.

**Procedure:**

1. Open **Active Directory Users and Computers**.
2. Locate `jsmith` and open **Properties**.
3. Navigate to **Account → Log On To**.
4. Add `COMP01` to the list of permitted computers.
5. Click **OK**, followed by **Apply/OK** in the main Properties window.
6. Re-query Active Directory to verify that the change was committed.

The resulting attribute was:

```text
LogonWorkstations : WIN-8QGPUAN7QO8,COMP01
```

**Important:** The first verification attempt still showed only the domain controller because the ADUC change had not yet been applied. After saving the change, PowerShell returned both workstations.

## 5. Validation

The updated Active Directory configuration was verified with:

```powershell
Get-ADUser -Identity "jsmith" -Properties Enabled,LockedOut,LogonWorkstations |
    Format-List Name,Enabled,LockedOut,LogonWorkstations
```

Verification showed that the account was enabled, not locked out, and permitted to log on to COMP01.

In the simulated support interaction, John confirmed that he could sign in and access his desktop and applications normally.

**Final Status:** Resolved.



### Inspect group membership


### Query a specific domain controller

```powershell
Get-ADUser -Identity "jsmith" -Server "WIN-8QGPUAN7QO8" -Properties LogonWorkstations |
    Format-List Name,LogonWorkstations
```

### PowerShell remediation alternative (not used in this ticket)

```powershell
Set-ADUser -Identity "jsmith" -LogonWorkstations "COMP01"
```

**Caution:** `Set-ADUser -LogonWorkstations` replaces the permitted workstation list. Include every authorized computer when using it; do not unintentionally remove existing approved entries.

## 7. Lessons Learned

- Exact Windows error messages can rapidly narrow the troubleshooting scope.
- ADUC **Account → Log On To** controls workstation-specific logon restrictions.
- PowerShell provides an independent method to confirm whether GUI changes were committed.
- Clicking **Add** in a dialog does not necessarily save the account change; verify with **Apply/OK** and a fresh directory query.
- Changes to on-premises AD workstation restrictions do not require an Entra Connect delta synchronization cycle.
- Validate both the directory configuration and the end user's ability to sign in before closing a ticket.
- Regular user access to a domain controller should be reviewed against security policy. Workstation logon restrictions are not a substitute for domain-controller logon rights controls.
- In production, investigate unexpected access-policy changes and follow organizational authorization procedures.

## 8. Service Desk Closure Notes

**Issue:** User unable to sign into COMP01 due to an Active Directory workstation logon restriction.

**Action:** Inspected the user's account in ADUC, identified the missing workstation, and added COMP01 to the permitted logon list after confirming authorized access.

**Verification:** Confirmed the saved `LogonWorkstations` attribute through PowerShell. Simulated user confirmed successful sign-in.

**Resolution:** Restored authorized workstation access.
