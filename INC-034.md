
# INC-034 — DNS Resolution Failure (Incorrect DNS Server)

**Date:** October 26, 2026  
**Priority:** P3 — Medium  
**Category:** Network Troubleshooting / DNS  
**Environment:** Windows 11, VMware Workstation  
**Affected Device:** Standalone Windows 11 test VM (referred to as COMP03; OS hostname reported COMP02)  
**Network Interface:** Ethernet0  
**Status:** Resolved

---

## 1. Incident Summary

A simulated Sales Department employee reported that their workstation appeared to have partial internet connectivity but could not access websites or the company's sales portal.

### User Report

> "Hi IT, my internet seems to be partially working. Some things on my computer appear connected, but I can't access the sales portal or most websites. I restarted my browser, but nothing changed. Could someone take a look?"

### Symptoms

- Websites failed to load.
- Browser displayed a DNS-related error.
- External IP connectivity remained functional.
- DNS hostname resolution failed.
- DHCP was enabled and a valid private IPv4 address was assigned.

### Root Cause

The workstation's Ethernet0 interface was manually configured to use an incorrect DNS server:

`192.0.2.53`

This address belongs to the reserved `192.0.2.0/24` documentation network and was not a usable DNS resolver in the lab environment.

As a result, the workstation could communicate with external IP addresses but could not resolve domain names through its configured DNS server.

### Resolution

Restored automatic DNS server configuration on Ethernet0, allowing Windows to use the DNS resolver provided through DHCP.

The workstation subsequently used `192.168.254.254` and successfully resolved domain names.

## 4. DNS Troubleshooting

### Step 2 — Test DNS Resolution

Command executed:

```powershell
nslookup google.com
```

Output:

```text
DNS request timed out.
    timeout was 2 seconds.
Server:  UnKnown
Address:  192.0.2.53

DNS request timed out.
    timeout was 2 seconds.
DNS request timed out.
    timeout was 2 seconds.
DNS request timed out.
    timeout was 2 seconds.
DNS request timed out.
    timeout was 2 seconds.
*** Request to UnKnown timed-out
```

### Analysis

The workstation attempted to query DNS server `192.0.2.53`, but the requests timed out.

This demonstrated that the configured DNS server was not responding to DNS queries.

Since external IP connectivity was already confirmed, the issue was isolated to DNS configuration or DNS service reachability rather than a general network outage.

### Step 3 — Inspect IP and DNS Configuration

Command executed:

```powershell

```

Relevant output:

```text
Windows IP Configuration

   Host Name . . . . . . . . . . . . : COMP02

Ethernet adapter Ethernet0:

   Connection-specific DNS Suffix  . : home
   Description . . . . . . . . . . . : Intel(R) 82574L Gigabit Network Connection

   DHCP Server . . . . . . . . . . . : 192.168.254.254
   DNS Servers . . . . . . . . . . . : 192.0.2.53
```

### Analysis

DHCP was enabled, and the workstation had received a valid private IPv4 address.

The default gateway and DHCP server were both configured as `192.168.254.254`.

However, the DNS server was configured as `192.0.2.53`.

This DNS address did not match the expected network configuration and was the primary suspect.

### Step 4 — Test Reachability of Configured DNS Server

Command executed:

```powershell
ping 192.0.2.53
```

Output:

```text
Pinging 192.0.2.53 with 32 bytes of data:
Request timed out.
Request timed out.
Request timed out.
Request timed out.

Ping statistics for 192.0.2.53:
    Packets: Sent = 4, Received = 0, Lost = 4 (100% loss)
```

### Analysis

The configured DNS server did not respond to ICMP echo requests.

However, a failed ping does not independently prove that a DNS server is unavailable, since some servers block ICMP.

The stronger evidence was that `nslookup` queries to the configured DNS server repeatedly timed out.

### Diagnostic Conclusion

The workstation had:

- A valid DHCP-assigned IPv4 address.
- A functioning default gateway.
- Successful external IP connectivity.
- An incorrect DNS server.
- Failed DNS resolution.

**Root cause identified: Incorrect manually configured DNS server on Ethernet0.**

## 5. Remediation

### Step 1 — Restore Automatic DNS Configuration

Command executed in Administrator PowerShell:

```powershell
Set-DnsClientServerAddress `
    -InterfaceAlias "Ethernet0" `
    -ResetServerAddresses
```

### Command Explanation

| Parameter | Purpose |
|---|---|
| `Set-DnsClientServerAddress` | Modifies DNS server configuration |
| `-InterfaceAlias "Ethernet0"` | Targets the affected network interface |
| `-ResetServerAddresses` | Removes manually configured DNS servers and restores automatic configuration |

This allowed the workstation to use DNS settings supplied by DHCP.

The remediation did not require changing the workstation's IPv4 address, subnet mask, or default gateway.

## 8. DHCP vs. DNS — Key Differences

### DHCP

Dynamic Host Configuration Protocol automatically provides network configuration to clients.

Typical settings include:

- IPv4 address
- Subnet mask
- Default gateway
- DNS servers

If DHCP fails and no valid static configuration exists, Windows may assign an APIPA address.

### DNS

Domain Name System translates hostnames into IP addresses.

Example:

```text
google.com → 142.251.210.142
```

If DNS fails while IP connectivity remains functional, users may be unable to access websites by hostname even though the network connection itself is working.

### Comparison With INC-033

| Characteristic | INC-033 | INC-034 |
|---|---|---|
| Root Cause | DHCP disabled | Incorrect DNS server |
| DHCP Enabled | No | Yes |
| IPv4 Address | 169.254.241.129 | 192.168.254.78 |
| Default Gateway | Missing | Present |
| External IP Ping | Failed | Successful |
| DNS Resolution | Failed | Failed |
| Remediation | Re-enable DHCP | Restore automatic DNS |
| Final Result | Connectivity restored | Connectivity restored |

**Key distinction:** INC-033 involved invalid IPv4 configuration. INC-034 involved DNS resolution failure despite working IP connectivity.

## 9. Lessons Learned

### Technical Lessons

1. Successful IP connectivity does not guarantee successful DNS resolution.
2. `ping 8.8.8.8` helps distinguish basic external IP connectivity from hostname resolution.
3. `nslookup` is a direct way to investigate DNS resolution failures.
4. A valid DHCP lease does not guarantee that manually configured DNS settings are correct.
5. DNS server settings can be restored without resetting the entire network interface.
6. A DNS server that does not respond to ping is not necessarily unavailable; DNS query results provide stronger evidence.
7. DNS settings should match the intended environment, particularly on Active Directory domain-joined workstations.

### Troubleshooting Lessons

- Test connectivity before modifying settings.
- Separate IP addressing, routing, and DNS into different diagnostic categories.
- Identify the smallest configuration change needed to restore service.
- Verify both command-line connectivity and actual browser functionality.
- Record pre-remediation and post-remediation outputs.
- Confirm that the reported symptom is resolved before closing the ticket.

### PowerShell Lessons

`Get-` commands generally retrieve configuration information:

```powershell
Get-DnsClientServerAddress
```

`Set-` commands modify configuration:

```powershell
Set-DnsClientServerAddress
```

Understanding command structure and the purpose of parameters is more important than memorizing exact syntax.

### Key Takeaway

When a workstation can successfully ping an external IP address but cannot access websites by hostname, DNS configuration is a primary area to investigate.

Comparing IP connectivity tests, DNS lookup results, and interface configuration allows a technician to identify DNS-related failures without unnecessarily resetting functioning network settings.
