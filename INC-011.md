## 5. Root Cause Analysis

**Immediate Root Cause:** The `rbrooks` account was disabled in Active Directory.

A disabled domain account cannot authenticate normally against Active Directory Domain Services.

The employee's password was not identified as the cause of the incident.

### Important Distinction

A disabled account is different from:

- An account locked out by repeated incorrect password attempts.
- An expired password.
- An expired account.
- An incorrect username or password.
- A workstation network connectivity issue.

Each condition may require a different remediation.

**Lab Cause:** Controlled PowerShell fault injection.

**Production Consideration:** In a real organization, the technician should determine whether the account was intentionally disabled by HR, security, or an administrator before restoring access.

---

## 6. Remediation

### Step 1 — Re-enable the Account

Using Active Directory Users and Computers:

1. Located the `rbrooks` user object.
2. Opened the account properties.
3. Unchecked the option indicating that the account was disabled.
4. Clicked **Apply** to save the change.
5. Refreshed the ADUC interface.

**Result:** The account was re-enabled.

### Equivalent PowerShell Command

The following command performs the equivalent administrative action:

```powershell
Enable-ADAccount -Identity "rbrooks"
```

**Note:** This PowerShell command is documented as an alternative. The actual remediation was performed using the ADUC graphical interface.

### Optional Verification Command

## 8. Security and Authorization Considerations

Although this was a straightforward L1 technical fix, account re-enablement has security implications.

A user account might be intentionally disabled because of:

- Employee termination or offboarding.
- Leave of absence.
- Suspected account compromise.
- HR or security restrictions.
- Administrative action.

Before re-enabling an account in production, the technician should:

1. Verify the requester's identity using an approved process.
2. Check the account's current status.
3. Review the available ticket history or administrative notes.
4. Confirm that re-enablement is authorized.
5. Escalate to IAM, HR, or security if the reason for disabling is unclear.
6. Document the change and verify access.

**Lab Limitation:** Authorization and audit-log review were not simulated in this exercise.

## 10. Lessons Learned

1. **Read the exact error message.** Windows sign-in errors can point directly to an account-state problem.
2. **ADUC provides useful visual indicators.** The disabled-account icon can quickly reveal the issue.
3. **Disabled and locked accounts are different.** Re-enabling an account and unlocking an account are separate administrative actions.
4. **GUI troubleshooting is valid.** PowerShell is useful for automation and verification, but ADUC can resolve straightforward account issues efficiently.
5. **Account restoration requires authorization.** A disabled account may reflect an intentional security or HR decision.
6. **Always obtain end-user confirmation.** The incident is not fully validated until the employee can access the affected service again.
7. **Document the actions performed.** A complete ticket should include the reported issue, findings, remediation, and verification.
