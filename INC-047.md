
# INC-047 — SMB Access Denied: Share and NTFS Permission Troubleshooting

**Date:** October 30, 2026  
**Category:** Windows Server / SMB / NTFS / Active Directory / IAM  
**Ticket Type:** Simulated Access Permission Incident  
**Environment:** Windows Server 2022, Windows 11, VMware Workstation  
**Status:** Resolved — Direct User Permission Workaround  
**Affected User:** ADEN\jsmith  
**Affected Resource:** `\\192.168.17.128\Department`

---

## 1. Incident Summary

A simulated access-permission incident was conducted in an Active Directory environment.

The affected employee, `ADEN\jsmith`, could access a departmental SMB shared folder and open existing documents but could not create new files.

Windows File Explorer displayed:

> Destination Folder Access Denied  
> You need permission to perform this action.

The investigation focused on identifying the relationship between SMB share permissions, NTFS permissions, Active Directory security-group membership, and Windows authentication sessions.

A dedicated AD security group was created and granted the appropriate permissions. Although the server-side configuration was verified, the new group did not appear in the client's displayed Windows logon token.

To complete the lab without extending the investigation, direct SMB Change and NTFS Modify permissions were granted to the affected test user.

**Outcome:** The user reported that access was restored following the direct permission change.

**Important:** Direct user permissions were used as a controlled lab workaround. Group-based permissions remain the preferred administrative approach.

## 3. User-Reported Problem

### Simulated Ticket

**User:** John Smith (`ADEN\jsmith`)

**Issue:**

"I can open the department's shared folder and read documents, but I can't create a new document."

### Expected Behavior

An authorized employee should be able to:

1. Access the departmental share.
2. Open existing files.
3. Create new files.
4. Edit and save documents.

### Actual Behavior

The employee could open:

```text
\\192.168.17.128\Department
```

And read:

```text
Welcome.txt
```

However, attempting to create a new text document produced:

```text
Destination Folder Access Denied

You need permission to perform this action.
```

This established that basic SMB connectivity and read access were functional, but the requested write operation was denied.

## 4. Initial Share Configuration

The Department share was created during INC-046 using:

```powershell
New-SmbShare `
    -Name "Department" `
    -Path "C:\LabShares\Department" `
    -ReadAccess "ADEN\Domain Users" `
    -FullAccess "ADEN\Domain Admins"
```

### Initial Permissions

| Security Principal | SMB Permission |
|---|---|
| ADEN\Domain Users | Read |
| ADEN\Domain Admins | Full |

The original share configuration permitted standard domain users to read files but did not grant them Change access.

This was consistent with the reported inability to create new files.

### Key Concept

SMB share permissions and NTFS permissions are separate access-control layers.

For a network file operation to succeed, both layers must permit the requested action.

A user with NTFS Modify permission can still be prevented from writing if the SMB share grants only Read access.

---

## 5. Investigation — Inspect SMB Permissions

On DC01, opened elevated PowerShell.

Executed:

```powershell
Get-SmbShareAccess -Name "Department"
```

The initial share configuration granted:

```text
ADEN\Domain Admins  Allow  Full
ADEN\Domain Users   Allow  Read
```

**Finding:** The affected user was a standard domain user accessing a share configured for read-only access.

This established an insufficient SMB share permission for the requested write operation.

---

## 6. Remediation Attempt 1 — Group-Based Access Control

Rather than granting every domain user write access, a dedicated AD security group was created.

### 6.1 Import Active Directory Module

On DC01:

```powershell
Import-Module ActiveDirectory
```

### 6.2 Create Security Group

```powershell
New-ADGroup `
    -Name "SG-Department-Modify" `
    -SamAccountName "SG-Department-Modify" `
    -GroupScope Global `
    -GroupCategory Security
```

This created a domain security group intended for users authorized to modify departmental files.

### 6.3 Add the User

```powershell
Add-ADGroupMember `
    -Identity "SG-Department-Modify" `
    -Members "jsmith"
```

### 6.4 Verify Membership

```powershell
Get-ADGroupMember -Identity "SG-Department-Modify" |
    Select-Object Name, SamAccountName
```

**Observed output:**

```text
Name        SamAccountName
----        --------------
John Smith  jsmith
```

**Result:** Active Directory confirmed that `jsmith` belonged to the new security group.

---

## 7. Grant SMB Change Permission

On DC01:

```powershell
Grant-SmbShareAccess `
    -Name "Department" `
    -AccountName "ADEN\SG-Department-Modify" `
    -AccessRight Change `
    -Force
```

### Verify

```powershell
Get-SmbShareAccess -Name "Department"
```

**Observed output:**

```text
AccountName                AccessControlType AccessRight
-----------                ----------------- -----------
ADEN\Domain Admins         Allow             Full
ADEN\Domain Users          Allow             Read
ADEN\SG-Department-Modify  Allow             Change
```

**Result:** The dedicated security group had SMB Change access.

The existing Domain Users Read permission remained unchanged.

## 8. Grant NTFS Modify Permission

On DC01:

```powershell
icacls "C:\LabShares\Department" /grant "ADEN\SG-Department-Modify:(OI)(CI)M"
```

### Parameter Explanation

| Parameter | Meaning |
|---|---|
| `/grant` | Adds an Allow access-control entry |
| `(OI)` | Object inheritance — files |
| `(CI)` | Container inheritance — subfolders |
| `M` | Modify permission |

### Verify NTFS Permissions

```powershell
icacls "C:\LabShares\Department"
```

**Observed output:**

```text
C:\LabShares\Department ADEN\SG-Department-Modify:(OI)(CI)(M)
                        NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
                        BUILTIN\Administrators:(I)(OI)(CI)(F)
                        BUILTIN\Users:(I)(OI)(CI)(RX)
                        BUILTIN\Users:(I)(CI)(AD)
                        BUILTIN\Users:(I)(CI)(WD)
                        CREATOR OWNER:(I)(OI)(CI)(IO)(F)

Successfully processed 1 files; Failed processing 0 files
```

### Interpretation

The dedicated group had Modify access at the NTFS layer.

The output also showed inherited permissions for local built-in groups.

**Important:** The presence of an NTFS Modify entry does not independently prove that the user's active SMB authentication session contains the required group membership.

## 9. Client Authentication Investigation

On COMP01, signed in as `ADEN\jsmith`, executed:

```powershell
whoami
```

**Observed output:**

```text
aden\jsmith
```

Then:

```powershell
whoami /groups
```

The displayed group list did not include:

```text
SG-Department-Modify
```

This was significant because the domain controller confirmed that `jsmith` belonged to the group.

### Potential Explanation

Windows access tokens contain security identifiers associated with the authenticated session.

Changes to Active Directory group membership do not necessarily update an existing interactive logon token immediately.

A new sign-in can refresh group membership information.

However, the absence of the group from the displayed interactive token does not conclusively prove which group memberships were evaluated in the remote SMB session.

### Additional Observation

After the group-based permission changes, the user reported being able to modify the existing `Welcome.txt` document but still could not create a new document.

This suggested that different file and directory operations were being permitted.

Possible contributing factors included:

- File-level versus directory-level permissions.
- Existing inherited NTFS permissions.
- An authentication token that had not incorporated the new group.
- An existing SMB connection using previously established credentials.

The precise cause of the remaining file-creation failure was not conclusively isolated.

---

## 10. Remediation Attempt 2 — Direct User Permissions

To complete the isolated homelab scenario without further authentication troubleshooting, direct permissions were granted to the affected user.

**This was a lab-specific workaround, not the preferred production solution.**

### 10.1 Grant SMB Change Access

On DC01:

```powershell
Grant-SmbShareAccess `
    -Name "Department" `
    -AccountName "ADEN\jsmith" `
    -AccessRight Change `
    -Force
```

This added an explicit SMB Change permission for the affected account.

### 10.2 Grant NTFS Modify Access

```powershell
icacls "C:\LabShares\Department" /grant "ADEN\jsmith:(OI)(CI)M"
```

This granted the user NTFS Modify access to the folder, files, and subfolders.

### 10.3 Verify the Configuration

Reference commands:

```powershell
Get-SmbShareAccess -Name "Department"
```

```powershell
icacls "C:\LabShares\Department"
```

These commands can confirm that the direct permission entries exist.

### Result

Following the direct permission change, the user reported that access was granted.

The direct grant was therefore accepted as the practical resolution for the lab.

**Verification limitation:** The conversation did not capture a separate successful `Test-Write.txt` creation and reopen test after the final change.

---

## 11. Root Cause and Resolution Assessment

### Confirmed Initial Cause

The original SMB share granted `ADEN\Domain Users` Read permission.

Read-only share access was insufficient for creating new documents over SMB.

### Group-Based Remediation

The following were successfully configured:

- Dedicated AD security group.
- `jsmith` membership in that group.
- SMB Change permission.
- NTFS Modify permission.

However, the client's displayed interactive token did not include the new group, and file creation remained unsuccessful.

### Final Workaround

Direct SMB Change and NTFS Modify permissions were assigned to `ADEN\jsmith`.

The user subsequently reported restored access.

### What Remains Unresolved

The exact reason that the group-based configuration did not immediately restore file creation was not conclusively determined.

Potential explanations include authentication-session behavior and differences between file-level and directory-level permissions.

The incident should not be described as a confirmed AD replication failure, broken NTFS inheritance, or corrupted Windows authentication token.

No evidence established those specific causes.

## 12. Knowledge Base — SMB Permission Troubleshooting

### Step 1 — Confirm User Identity

On the affected workstation:

```powershell
whoami
```

Inspect group memberships:

```powershell
whoami /groups
```

### Step 2 — Verify Network Connectivity

```powershell
Test-NetConnection 192.168.17.128 -Port 445
```

Expected:

```text
TcpTestSucceeded : True
```

This verifies TCP connectivity to the SMB service.

### Step 3 — Verify the Share Exists

On the server:

```powershell
Get-SmbShare -Name "Department"
```

### Step 4 — Inspect SMB Share Permissions

```powershell
Get-SmbShareAccess -Name "Department"
```

Look for:

- Read
- Change
- Full
- Explicit Deny entries

### Step 5 — Inspect NTFS Permissions

```powershell
icacls "C:\LabShares\Department"
```

For a structured PowerShell view:

```powershell
(Get-Acl "C:\LabShares\Department").Access |
    Format-Table IdentityReference, FileSystemRights, AccessControlType, IsInherited -AutoSize
```

### Step 6 — Verify AD Group Membership

On a domain controller or authorized management workstation:

```powershell
Get-ADGroupMember -Identity "SG-Department-Modify"
```

To inspect the user's direct AD group memberships:

```powershell
Get-ADPrincipalGroupMembership -Identity "jsmith" |
    Select-Object Name
```

### Step 7 — Inspect Active SMB Connections

On the client:

```powershell
Get-SmbConnection |
    Format-Table ServerName, ShareName, UserName, Dialect
```

On the server:

```powershell
Get-SmbSession |
    Format-Table SessionId, ClientComputerName, ClientUserName
```

These commands can help identify active sessions and the accounts used to access SMB resources.

### Step 8 — Refresh Authentication When Appropriate

If a user was recently added to an AD group:

1. Save the user's work.
2. Sign out of Windows.
3. Sign back in using the domain account.
4. Verify group membership.
5. Reconnect to the shared resource.
6. Retest the denied operation.

Do not assume that changing AD membership automatically updates every existing authentication session.

### Step 9 — Verify the Requested Operation

A complete verification should test the specific operation that originally failed.

For this incident:

1. Open the shared folder.
2. Create a new text document.
3. Enter sample text.
4. Save the file.
5. Reopen and edit it.
6. Confirm that the changes persist.

Successful reading alone is not sufficient to verify restored write access.

## 13. Permission Reference

### SMB Share Permissions

| Permission | Typical Capabilities |
|---|---|
| Read | Read and list shared files |
| Change | Read, create, modify, and delete files, subject to NTFS permissions |
| Full | Change-level operations plus additional share-level control |

### NTFS Permissions

| Permission | Typical Capabilities |
|---|---|
| Read | View file contents |
| Read & Execute | Read files and execute permitted programs |
| Write | Create files and write data, subject to applicable object permissions |
| Modify | Read, write, modify, and delete files |
| Full Control | Modify permissions and take ownership-related actions where permitted |

### Effective Network Permissions

Both SMB and NTFS permissions apply when accessing files over a network share.

| SMB Permission | NTFS Permission | Typical Effective Access |
|---|---|---|
| Read | Modify | Read |
| Change | Modify | Modify |
| Full | Read | Read |
| Full | Modify | Modify |

These examples assume no additional Deny entries or other restrictions.

## 14. Production Best Practices

### Prefer Security Groups

Recommended pattern:

```text
AD User
   |
   v
Department Security Group
   |
   +--> SMB Share Permission
   |
   +--> NTFS Folder Permission
```

This allows administrators to manage access through group membership instead of creating individual permission entries for every employee.

### Follow Least Privilege

Only grant the access required for the employee's role.

For example:

- Read for employees who only need to view documents.
- Modify for authorized contributors.
- Full Control only when administratively justified.

### Require Authorization

A help desk technician should verify that the employee is authorized to receive access before changing permissions.

Depending on organizational policy, permission changes may require manager approval or escalation.

### Avoid Broad Access Changes

Do not grant `Everyone` Full Control simply to resolve an Access Denied error.

This can expose departmental data and create unnecessary security risks.

### Document Temporary Workarounds

Direct user permissions can be useful for controlled troubleshooting, but should be reviewed and removed when a group-based configuration is working.

## 15. Optional Cleanup — Remove Direct User Grants

**Not performed during this incident.**

After the group-based permissions are verified and functioning, direct user grants can be removed.

### Remove Direct SMB Permission

```powershell
Revoke-SmbShareAccess `
    -Name "Department" `
    -AccountName "ADEN\jsmith" `
    -Force
```

### Remove Explicit NTFS Grant

```powershell
icacls "C:\LabShares\Department" /remove:g "ADEN\jsmith"
```

**Caution:** Review the current ACL before running cleanup commands. The NTFS command removes explicit Allow entries for the specified account on the target directory; it does not recursively remove every explicit entry from existing child objects.

Do not remove permissions until the intended group-based access has been tested successfully.
