
# INC-045 — Network Printer Connectivity Failure

**Date:** October 29, 2026  
**Category:** Windows 11 / Network Troubleshooting / Printer Support  
**Environment:** COMP02 — Windows 11 VM (VMware Workstation)  
**Affected Device:** HP Color LaserJet MFP M281cdw  
**Affected Network Adapter:** Ethernet0 — Intel(R) 82574L Gigabit Network Connection  
**Incident Type:** Simulated network connectivity failure  
**Status:** Resolved  
**Resolution:** Reconnected the virtual network adapter and verified successful physical printing.

---

## 1. Incident Summary

A simulated network printer connectivity incident was performed on COMP02 to investigate a printing failure caused by loss of workstation network connectivity.

The HP Color LaserJet MFP M281cdw was installed and functioning before the incident. A physical test page was successfully printed, establishing a working baseline.

The virtual network adapter was then intentionally disconnected through VMware Workstation to simulate a disconnected Ethernet cable or inactive network link.

PowerShell diagnostics confirmed that the network adapter had lost its connection and no longer possessed an active IPv4 configuration.

The virtual adapter was reconnected, restoring network connectivity and access to the printer.

**Outcome:** COMP02 successfully regained network connectivity, reached its default gateway, and printed a physical test page.

## 3. Fault Injection — Disconnect Virtual Ethernet

### 3.1 Simulated Incident

**User-reported scenario:**

> "My printer was working earlier, but now I can't print. The printer is still installed in Windows."

The objective was to simulate a workstation losing network connectivity while retaining its installed printer configuration.

### 3.2 Disconnect Network Adapter

In VMware Workstation:

1. Select COMP02.
2. Open `VM → Settings → Network Adapter`.
3. Locate the **Connected** checkbox.
4. Uncheck **Connected**.
5. Click **OK**.

The virtual Ethernet connection was disconnected without changing the printer driver, printer port, or Windows Print Spooler configuration.

**Safety:** This simulation affected COMP02's virtual network connection rather than the physical ThinkCentre host or network infrastructure.

## 4. Investigation — Identify the Network Failure

### 4.1 Check Network Adapter Status

```powershell
Get-NetAdapter |
    Format-Table Name, Status, LinkSpeed
```

**Observed output:**

```text
Name      Status       LinkSpeed
----      ------       ---------
Ethernet0 Disconnected 0 bps
```

**Interpretation:**

- The Ethernet adapter was still recognized by Windows.
- The adapter no longer had an active network link.
- Link speed had dropped from 1 Gbps to 0 bps.

This was evidence of a link-level connectivity failure.

**Key distinction:** The adapter was not missing or uninstalled. It was present but disconnected.

### 4.2 Inspect IP Configuration

```powershell
ipconfig /all
```

**Observed output:**

```text
Windows IP Configuration

   Host Name . . . . . . . . . . . . : COMP02
   Primary Dns Suffix  . . . . . .  :
   Node Type . . . . . . . . . . . . : Hybrid
   IP Routing Enabled. . . . . . .  : No
   WINS Proxy Enabled. . . . . . .  : No

   Physical Address. . . . . . . . : 00-0C-29-6E-C4-28
   DHCP Enabled. . . . . . . . . .  : Yes
   Autoconfiguration Enabled . . . : Yes
```

**Findings:**

- Windows reported `Media disconnected`.
- No active IPv4 address was displayed.
- No default gateway was displayed.
- DHCP remained enabled, but the interface had no active link.

### 4.3 Test External Connectivity

An attempt to ping Google failed while the adapter was disconnected.

This was consistent with the workstation having no active network connectivity.

However, a failed external ping alone cannot distinguish between:

- Physical connectivity failure
- Routing failure
- DNS failure
- Firewall restrictions
- Remote host unavailability

The decisive evidence was the combination of:

```text
Ethernet0: Disconnected
LinkSpeed: 0 bps
Media disconnected
```

### 4.4 Diagnostic Conclusion

The workstation's network link was disconnected.

This explained why network-dependent services, including communication with a network printer, would be unavailable.

Further investigation of printer drivers, DNS, or the Print Spooler was not necessary until the workstation's network connectivity was restored.

## 5. Root Cause Analysis

**Root Cause:** The VMware virtual network adapter's Connected setting was intentionally disabled.

**Affected Component:** COMP02 Ethernet0 network interface.

**Failure Domain:** Network link connectivity.

**OSI Layer:** Primarily Layer 1 (physical/link availability), simulated through VMware's virtual network connection.

The operating system continued recognizing the virtual network adapter but detected that its network medium was disconnected.

### Why This Was Not a DHCP Failure

DHCP remained enabled.

The workstation could not communicate over the disconnected interface to obtain or use a DHCP lease.

A DHCP-specific issue would more typically involve an active network link with unsuccessful address assignment, potentially resulting in an APIPA address.

In this incident, Windows explicitly reported:

```text
Media disconnected
```

Therefore, the investigation focused on restoring the network link before troubleshooting DHCP.

### Why This Was Not a Printer Driver Failure

The printer remained installed with its existing Microsoft IPP Class Driver and WSD port configuration.

The known fault was the workstation's disconnected network adapter.

No evidence indicated that the printer driver required modification or reinstallation.

## 6. Resolution — Restore Network Connectivity

### 6.1 Reconnect Virtual Ethernet

In VMware Workstation:

1. Select COMP02.
2. Navigate to `VM → Settings → Network Adapter`.
3. Check **Connected**.
4. Click **OK**.

No changes were made to the printer configuration.

### 6.2 Verify Adapter Recovery

```powershell
Get-NetAdapter
```

**Observed output:**

```text
Name      InterfaceDescription                         ifIndex Status MacAddress        LinkSpeed
----      --------------------                         ------- ------ ----------        ---------
Ethernet0 Intel(R) 82574L Gigabit Network Connection   8       Up     00-0C-29-6E-C4-28 1 Gbps
```

**Result:** Ethernet0 returned to `Up` with a negotiated link speed of 1 Gbps.

### 6.3 Verify IP Address Recovery

```powershell
ipconfig /all
```

The workstation regained its private IPv4 configuration.

The restored source address was subsequently confirmed as:

```text
192.168.254.78
```

### 6.4 Test Gateway Connectivity

```powershell
Test-NetConnection 192.168.254.254
```

**Observed output:**

```text
ComputerName           : 192.168.254.254
RemoteAddress          : 192.168.254.254
InterfaceAlias         : Ethernet0
SourceAddress          : 192.168.254.78
PingSucceeded          : True
PingReplyDetails (RTT) : 1 ms
```

**Interpretation:**

- The workstation had a usable IPv4 address.
- The Ethernet interface was operational.
- The default gateway was reachable.
- ICMP communication succeeded.
- The measured round-trip time was 1 ms.

This confirmed restoration of local network connectivity.

**Note:** Gateway connectivity does not independently prove that every remote device or service is reachable. Printer functionality must be verified separately.

## 8. Reusable Knowledge Base — Network Printer Troubleshooting

The following workflow can be applied to real-world printer connectivity incidents.

### Phase A — Determine the Scope

Ask the user:

- Is the printer installed in Windows?
- Can other users print to the same printer?
- Can this workstation print to other printers?
- Is the workstation connected to the network?
- Did the issue begin after a network, hardware, or workstation change?

These questions help distinguish between workstation-wide, network-wide, and printer-specific failures.

### Phase B — Inspect Printer Configuration

```powershell
Get-Printer |
    Format-Table Name, PrinterStatus, DriverName, PortName
```

Check whether the printer exists and inspect its driver, status, and port.

For additional port information:

```powershell
Get-PrinterPort |
    Format-Table Name, PrinterHostAddress, PortNumber
```

**Note:** WSD ports may not expose a conventional printer IP address through `PrinterHostAddress`.

### Phase C — Inspect Network Link

```powershell
Get-NetAdapter |
    Format-Table Name, Status, LinkSpeed
```

If the adapter reports `Disconnected`, investigate the local network connection before proceeding to DNS or printer-specific troubleshooting.

For physical workstations, check:

- Ethernet cable connection
- Docking station connection
- Network switch port
- Network interface status
- Network adapter hardware

For virtual machines, inspect the virtual NIC's connection settings.

### Phase D — Inspect IP Configuration

```powershell
ipconfig /all
```

Look for:

- IPv4 address
- Subnet mask
- Default gateway
- DHCP server
- DNS servers
- Media state

Common interpretations:

| Observation | Potential Explanation |
|---|---|
| Media disconnected | No active network link |
| 169.254.x.x address | APIPA; DHCP assignment may have failed |
| Valid IPv4 but no gateway | Incomplete or intentionally local-only configuration |
| Incorrect DNS server | Possible name-resolution failure |
| Valid IP and gateway | Proceed with connectivity tests |

These observations guide further investigation but are not sufficient alone to identify every root cause.

### Phase E — Test Connectivity

Test the configured default gateway:

```powershell
Test-NetConnection 192.168.254.254
```

Replace the example address with the actual gateway for the affected workstation.

If the printer's IP address is known:

```powershell
Test-NetConnection -ComputerName <PRINTER_IP>
```

For a printer using a Standard TCP/IP port with RAW printing on TCP 9100:

```powershell
Test-NetConnection -ComputerName <PRINTER_IP> -Port 9100
```

**Important:** TCP 9100 is not universal. WSD, IPP, and other printer configurations may use different protocols and ports.

Do not assume a failed TCP 9100 test indicates an outage unless the printer is expected to use that port.

### Phase F — Inspect Print Services

If the network connection is healthy, inspect the Print Spooler:

```powershell
Get-Service Spooler
```

Inspect installed printers:

```powershell
Get-Printer
```

Inspect the print queue:

```powershell
Get-PrintJob -PrinterName "PRINTER_NAME"
```

Replace `PRINTER_NAME` with the installed printer name.

Investigate whether the problem involves a stopped service, stuck job, incorrect printer port, driver issue, or device connectivity.

### Phase G — Restore and Verify

After resolving the identified fault:

1. Confirm the network adapter is operational.
2. Confirm the workstation has the expected IP configuration.
3. Test connectivity to the appropriate network destination.
4. Print a physical test page.
5. Confirm the user can resume printing.

Do not close the incident solely because the printer status displays `Normal`.

## 10. Key Takeaways

### 10.1 Installed Does Not Mean Reachable

A printer can remain installed in Windows even when the workstation cannot communicate with it.

Printer installation and network connectivity are separate conditions.

### 10.2 Diagnose the Lowest Relevant Layer First

When Windows reports `Media disconnected`, investigate link availability before DHCP, DNS, or application-layer services.

This prevents unnecessary driver reinstalls or Print Spooler restarts.

### 10.3 Distinguish Link Failure from DHCP Failure

A disconnected adapter and an APIPA address represent different diagnostic situations.

- **Disconnected:** No active network link.
- **APIPA:** Interface may have an active link but lacks a usable DHCP-assigned IPv4 address.

### 10.4 Printer Status Is Not Definitive

A WSD printer may remain listed as `Normal` even when communication is interrupted or its status has not refreshed.

Functional printing provides stronger verification.

### 10.5 Verify Each Stage of Recovery

Successful troubleshooting should confirm:

1. Network link restored.
2. IP configuration restored.
3. Network communication restored.
4. Printing functionality restored.

A successful gateway ping does not substitute for a physical test print.
