
# INC-033 — Network Connectivity Failure (DHCP Disabled / APIPA)

**Date:** October 26, 2026  
**Priority:** P3 — Medium  
**Category:** Network Troubleshooting / Windows Endpoint Support  
**Environment:** Windows 11, VMware Workstation  
**Affected Device:** COMP03 (intended VM; Windows hostname reported COMP02 — verify)  
**Network Interface:** Ethernet0  
**Status:** Remediated — Connectivity Restored; Final Configuration Verification Pending

---

## 1. Incident Summary

A simulated Sales Department employee reported that their workstation could no longer access websites or an online sales portal.

### User Report

> "My computer was working fine yesterday, but today I can't access any websites. Chrome keeps saying the site can't be reached. I've restarted Chrome twice, but nothing changed."

### Impact

- Internet browsing unavailable.
- Web-based business applications inaccessible.
- Workstation assigned an APIPA address.
- No IPv4 default gateway configured.
- DNS resolution unsuccessful.

### Root Cause

DHCP was disabled on the workstation's Ethernet0 IPv4 interface.

The workstation had no valid static or DHCP-assigned IPv4 configuration. Windows assigned an Automatic Private IP Addressing (APIPA) address in the `169.254.0.0/16` range.

Without a valid default gateway, the workstation could not communicate normally with external networks.

**Important:** The fault was caused by the workstation's DHCP configuration. This did not establish that the DHCP server itself was malfunctioning.

## 3. Initial Investigation

### Step 1 — Inspect IP Configuration

Commands:

```powershell
ipconfig
ipconfig /all
```

Observed output:

```text
Ethernet adapter Ethernet0:

   DHCP Enabled. . . . . . . . . . . : No
   Autoconfiguration Enabled . . . . : Yes
   Autoconfiguration IPv4 Address. . : 169.254.241.129
   Subnet Mask . . . . . . . . . . . : 255.255.0.0
   Default Gateway . . . . . . . . . :
```

### Findings

**1. DHCP was disabled**

```text
DHCP Enabled: No
```

The workstation was not configured to request an IPv4 address automatically.

**2. Windows assigned an APIPA address**

```text
169.254.241.129
```

APIPA addresses belong to the `169.254.0.0/16` link-local range.

Windows may assign an APIPA address when automatic addressing is enabled but no usable IPv4 configuration is available.

**3. No default gateway was configured**

```text
Default Gateway:
```

Without an appropriate gateway, the workstation could not route ordinary IPv4 traffic to external networks.

### Initial Diagnosis

The combination of disabled DHCP, an APIPA address, and a missing default gateway indicated a local IPv4 configuration problem.

## 4. Connectivity Testing

### Test 1 — External IP Connectivity

Command:

```powershell
ping 8.8.8.8
```

Result:

```text
PING: transmit failed. General failure.
PING: transmit failed. General failure.
PING: transmit failed. General failure.
PING: transmit failed. General failure.

Packets: Sent = 4, Received = 0, Lost = 4 (100% loss)
```

### Interpretation

The workstation could not successfully transmit ICMP traffic to an external IPv4 address.

Because the test used an IP address rather than a hostname, DNS resolution was not required.

This result was consistent with the workstation's missing default gateway and unusable IPv4 configuration.

**Troubleshooting lesson:** If an external IP address cannot be reached, investigate addressing, routing, adapters, and gateways before assuming DNS is the primary problem.

### Test 2 — DNS Resolution

Command:

```powershell
nslookup google.com
```

Result:

```text
Server:  UnKnown
Address:  fec0:0:0:ffff::1

*** UnKnown can't find google.com: No response from server
```

### Interpretation

The workstation could not successfully contact a DNS resolver.

However, DNS was not necessarily an independent root cause. The workstation's overall network configuration was already broken.

The priority was to restore valid IP configuration before investigating DNS further.

## 5. Root Cause Analysis

### Expected Network Behavior

Under normal conditions:

1. The workstation starts with DHCP enabled.
2. The DHCP client requests configuration from a DHCP server.
3. The server provides an available IPv4 address and additional settings.
4. The workstation configures its IP address, subnet mask, default gateway, and DNS settings.
5. The workstation can communicate with local and external networks.

### Actual Network Behavior

1. DHCP was disabled on Ethernet0.
2. No valid static IPv4 configuration was available.
3. Windows assigned an APIPA address.
4. No IPv4 default gateway was configured.
5. External IPv4 communication and DNS resolution failed.

### DHCP DORA Process

The standard DHCP lease acquisition process consists of:

- **Discover:** Client broadcasts to locate DHCP servers.
- **Offer:** DHCP server offers configuration.
- **Request:** Client requests the offered address.
- **Acknowledge:** Server confirms the lease.

With the DHCP client disabled, the workstation was not performing normal DHCP-based IPv4 address acquisition.

## 6. Remediation

### Step 1 — Enable DHCP

Command executed:

```powershell
Set-NetIPInterface `
    -InterfaceAlias "Ethernet0" `
    -AddressFamily IPv4 `
    -Dhcp Enabled
```

**Purpose:** Restore automatic IPv4 address assignment on Ethernet0.

This allows the workstation to request a DHCP lease.

### Step 2 — Attempted APIPA Removal

Command attempted:

```powershell
Remove-NetIPAddress `
    -InterfaceAlias "Ethernet0" `
    -IPAddress "169.254.77.25" `
    -Confirm:$false
```

Error:

```text
Remove-NetIPAddress : No matching MSFT_NetIPAddress objects found
```

### Why the Command Failed

The command referenced `169.254.77.25`, but the observed APIPA address was:

```text
169.254.241.129
```

The specified address was not found on Ethernet0.

### Lesson Learned

Never reuse an IP address from another ticket without confirming the current interface configuration.

Use:

```powershell
Get-NetIPAddress `
    -InterfaceAlias "Ethernet0" `
    -AddressFamily IPv4
```

**Important:** Manually removing an APIPA address is usually unnecessary when restoring DHCP. Windows can update the address configuration after successfully acquiring a DHCP lease.

### Step 3 — Restore Automatic DNS Configuration

Command executed:

```powershell
Set-DnsClientServerAddress `
    -InterfaceAlias "Ethernet0" `
    -ResetServerAddresses
```

**Purpose:** Restore automatic DNS server configuration.

This was appropriate for the standalone test workstation, which was expected to obtain DNS settings automatically.

**Enterprise note:** Domain-joined Windows clients generally need to use DNS servers capable of resolving the organization's Active Directory domain. Do not arbitrarily replace internal DNS servers with public DNS servers.

### Step 4 — Renew DHCP Lease

Command executed:

```powershell
ipconfig /renew
```

**Purpose:** Request updated DHCP configuration after enabling DHCP.

The complete renewed lease output was not captured.

## 9. Network Troubleshooting Decision Tree

### Scenario A — APIPA Address Present

Example:

```text
169.254.x.x
```

Investigate:

1. Is DHCP enabled?
2. Is the network adapter connected?
3. Is the DHCP server reachable?
4. Is the DHCP service available?
5. Is the client connected to the correct virtual or physical network?

Useful commands:

```powershell
ipconfig /all
Get-NetAdapter
Get-NetIPInterface -AddressFamily IPv4
```

### Scenario B — Valid IP Address, No Internet

Investigate:

1. Is the default gateway correct?
2. Can the workstation reach its gateway?
3. Is there a valid default route?
4. Can it reach an external IP?
5. Is a firewall or upstream network blocking traffic?

Useful commands:

```powershell
ipconfig /all
route print
ping 8.8.8.8
tracert 8.8.8.8
```

### Scenario C — IP Connectivity Works, Hostnames Fail

Investigate:

1. Which DNS servers are configured?
2. Are they reachable?
3. Can they resolve the requested hostname?
4. Is the DNS suffix appropriate?
5. Is the problem limited to one hostname or domain?

Useful commands:

```powershell
Get-DnsClientServerAddress
nslookup google.com
ipconfig /flushdns
```

### Scenario D — DNS Works, Website Still Fails

Investigate:

1. Can the workstation establish TCP connectivity?
2. Is the service listening on the expected port?
3. Is a firewall or proxy involved?
4. Is the issue browser-specific?
5. Is the destination service experiencing an outage?

Useful command:

```powershell
Test-NetConnection google.com -Port 443
```

## 10. Lessons Learned

### Technical Lessons

1. An APIPA address is a symptom of missing usable IPv4 configuration, not proof that the DHCP server itself is broken.
2. DHCP must be enabled on the client when automatic IPv4 configuration is expected.
3. A missing default gateway can prevent external IPv4 communication.
4. External IP connectivity and DNS resolution should be tested separately.
5. Restoring DHCP usually removes the need to manually delete an APIPA address.
6. Always inspect the current IP address before running commands that target a specific address.
7. DNS configuration must match the environment, especially for Active Directory clients.

### Troubleshooting Lessons

- Start by collecting evidence before changing configuration.
- Interpret command output rather than simply copying remediation commands.
- Use known-good configuration as a reference.
- Verify the actual service or application after making changes.
- Record failed commands and explain why they failed.
- Confirm the affected device before finalizing documentation.

### PowerShell Development

This incident reinforced the distinction between:

```powershell
Get-NetIPInterface
```

Used to inspect interface configuration.

And:

```powershell
Set-NetIPInterface
```

Used to modify interface configuration.

Understanding the purpose of a command and its parameters is more valuable than memorizing every character.

**Issue:** Workstation unable to access the internet.

**Root Cause:** DHCP disabled on Ethernet0, resulting in APIPA addressing and no usable default gateway.

**Corrective Action:** Re-enabled DHCP, restored automatic DNS configuration, and renewed DHCP settings.

**Result:** Private IPv4 addressing, DNS resolution, and browser connectivity reportedly restored.

**Status:** Remediated — Final device identity and post-fix configuration confirmation pending.

### Key Takeaway

A workstation displaying a `169.254.x.x` address should prompt investigation of DHCP and IP configuration. By examining the DHCP state, assigned IP address, default gateway, and connectivity tests, the technician can distinguish local addressing failures from DNS and upstream network problems.
