## 3. Controlled Fault Injection

### Objective

Simulate a realistic administrative configuration mistake in which an application installs successfully but Intune cannot recognize it.

### Fault Introduced

The existing Win32 application detection rule was modified in the Intune admin center.

**Navigation:**

Intune Admin Center → Apps → Windows → Windows apps → 7-Zip → Properties → Detection rules → Edit

The original filename was changed:

```text id="ueqv3m"
Original: 7z.exe
Modified: 7z-missing.exe
```

The installation directory remained unchanged:

```text id="2rx4cn"
C:\Program Files\7-Zip
```

### Configuration Comparison

| Setting | Working configuration | Injected configuration |
|---|---|---|
| Rule type | File | File |
| Path | `C:\Program Files\7-Zip` | `C:\Program Files\7-Zip` |
| Filename | `7z.exe` | `7z-missing.exe` |
| Detection method | File exists | File exists |

The modified rule was saved and applied.

### Scope of Change

Only the Intune detection rule was modified.

The following were not intentionally changed:

- Application installation files.
- Win32 application package.
- Installation command.
- Device assignment.
- Installed application binaries.
- Windows operating system configuration.

**Important:** The injected fault affected application detection, not the installed 7-Zip software itself.

## 6. Root Cause Analysis

### Root Cause

**Incorrect Win32 application detection rule.**

Microsoft Intune was configured to detect:

```text id="6cx4g1"
C:\Program Files\7-Zip\7z-missing.exe
```

However, the actual installed executable was:

```text id="u8q0yv"
C:\Program Files\7-Zip\7z.exe
```

Because the configured detection target did not exist, Intune could not correctly recognize the installed application.

### Technical Explanation

Win32 application management involves several distinct processes.

**1. Installation**

Intune runs the configured installation command on the endpoint.

**2. Detection**

Intune evaluates the configured detection rules to determine whether the application is installed.

**3. Reporting**

The endpoint reports installation and detection results to the Intune service.

These processes can produce different outcomes.

An application can be installed and functional while Intune reports a deployment failure because the detection rule is incorrect.

### Potential Consequences

Incorrect detection rules can lead to:

- Failed application deployment reporting.
- Repeated installation attempts.
- Unnecessary troubleshooting or escalation.
- Incorrect software inventory information.
- Confusion between application failures and management failures.

This is particularly relevant when managing custom Win32 application packages.

## 7. Remediation

### Corrective Action

The detection rule was identified as the configuration requiring correction.

The intended remediation was to restore the original filename.

**Navigation:**

Intune Admin Center → Apps → Windows → Windows apps → 7-Zip → Properties → Detection rules → Edit

Restore:

```text id="c4c3qv"
Path: C:\Program Files\7-Zip

File or folder: 7z.exe

Detection method: File or folder exists
```

Save the updated configuration.

### Why Reinstallation Was Not Necessary

The actual 7-Zip executable remained present and functional.

Therefore, rebuilding the application package or manually reinstalling 7-Zip was not the appropriate first remediation step.

The issue was isolated to the application's management configuration.

### Change Scope

The corrective action was limited to restoring the expected detection target.

No intentional modification to the installed application was required.

## 9. Intune Reporting and Synchronization

Microsoft Intune does not continuously reevaluate every Win32 application in real time.

After a detection rule is modified, the following processes may occur:

1. Updated application policy becomes available.
2. The managed endpoint receives or processes the policy.
3. Intune Management Extension reevaluates application detection.
4. The endpoint reports the result.
5. The Intune admin center displays the updated status.

### Important Observation

Refreshing the Intune admin center does not force the endpoint to immediately reevaluate an application.

Similarly, initiating a Windows MDM sync does not guarantee an immediate Win32 application detection cycle.

### Operational Decision

Rather than repeatedly refreshing the portal, the technician paused further investigation and allowed additional time for policy processing and reporting.

**Ticket disposition:** Remediated or correction identified, pending final verification.

If the status remains incorrect after an appropriate observation period, additional troubleshooting is required.

# Reusable Troubleshooting Guide

## 10. Diagnosing Intune Application Detection Failures

This workflow can be reused when an application is installed but Intune reports it as missing or failed.

### Phase 1 — Confirm the User's Complaint

Ask:

- Can the application launch?
- When did the problem begin?
- Does the application display an error?
- Is the issue affecting one device or multiple devices?
- Does Intune report Failed, Not installed, or Not applicable?

Record the actual symptoms before modifying the deployment.

### Phase 2 — Verify Application Installation

Check whether the application exists.

Example:

```powershell id="1dtl92"
Test-Path "C:\Program Files\<Application>\<Executable>.exe"
```

If the application is present, verify that it launches and functions.

### Phase 3 — Review Intune Detection Rules

Navigate to:

Intune → Apps → Windows → Windows apps → Application → Properties → Detection rules

Check:

- Detection rule type.
- File or registry path.
- Filename.
- Detection method.
- File version requirements.
- 32-bit versus 64-bit behavior.

Compare the rule against the actual installed application.

### Phase 4 — Review Deployment Configuration

If the detection rule is correct, investigate:

- Application assignment.
- Device eligibility.
- Installation context.
- Installation commands.
- Installer exit codes.
- Dependencies.
- Conflicting deployments.

Do not assume every installation failure is caused by detection.

### Phase 5 — Inspect Management Extension Logs

On the managed endpoint, locate:

```text id="o4td4x"
C:\ProgramData\Microsoft\IntuneManagementExtension\Logs
```

Relevant logs include:

| Log | Purpose |
|---|---|
| IntuneManagementExtension.log | General extension processing |
| AppWorkload.log | Win32 application activity |
| AppActionProcessor.log | Detection and applicability |
| AgentExecutor.log | PowerShell script execution |

Example:

```powershell id="mx99ns"
Get-Content `
    "C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AppWorkload.log" `
    -Tail 80
```

Search for relevant entries:

```powershell id="b8pp97"
Select-String `
    -Path "C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AppWorkload.log" `
    -Pattern "install","detect","error" |
    Select-Object -Last 30
```

Logs may identify applications by internal IDs rather than friendly display names.

### Phase 6 — Apply the Smallest Corrective Change

Once the root cause is established:

1. Modify only the incorrect setting.
2. Save the updated configuration.
3. Avoid unnecessary application reinstallation.
4. Allow the endpoint to process the updated policy.
5. Verify the resulting installation state.

For production deployments, use a test group and follow change-management procedures before changing shared application configurations.

### Phase 7 — Verify Resolution

Confirm:

- Application functions on the endpoint.
- Detection rule matches the installed application.
- Intune reports Installed.
- No new installation errors occur.
- Other targeted devices remain unaffected.

Document any remaining reporting delays or unresolved errors.

## 11. Lessons Learned

### 1. Installation and Detection Are Separate

An application may install successfully while Intune fails to recognize it.

### 2. A Small Configuration Error Can Affect Deployment Reporting

Changing a single filename in a detection rule can cause an otherwise functional application to be reported as failed.

### 3. Verify the Endpoint Before Reinstalling

Checking actual files and application functionality can prevent unnecessary reinstallations.

### 4. PowerShell Provides Fast Diagnostic Evidence

The `Test-Path` cmdlet can quickly establish whether the expected executable exists.

### 5. Intune Reporting Is Not Always Immediate

Portal refreshes and device synchronization do not guarantee immediate Win32 application reevaluation.

### 6. Troubleshooting Should Be Evidence-Based

Compare:

- User symptoms.
- Actual endpoint state.
- Management configuration.
- Deployment reporting.

Do not rely on a single status indicator.

### 7. Change Only What Is Necessary

Correcting the detection rule is preferable to rebuilding a working application package.

### 8. Distinguish Remediation From Verification

Identifying and correcting a root cause does not automatically mean the ticket is fully resolved.

Final verification is a separate operational step.
