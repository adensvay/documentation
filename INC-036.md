
# INC-036 — Web Access Failure Caused by Outbound Windows Firewall Rule

**Date:** October 26, 2026  
**Priority:** P3 — Medium  
**Category:** Network Troubleshooting / Windows Defender Firewall  
**Environment:** Windows 11, VMware Workstation  
**Affected Hostname:** COMP02  
**Network Interface:** Ethernet0  
**Status:** Resolved

---

## 1. Incident Summary

A simulated employee reported that several websites were inaccessible despite Windows indicating an active network connection.

### User Report

**Reported by:** Amanda Morgan — Operations

> "Hi IT, something is wrong with my computer's connection. I can see that I'm connected to the network, but I can't reliably access the websites I need for work. I've already restarted Chrome, and the issue is still happening. Other employees don't seem to have the same problem. Can you investigate?"

### Technician Follow-Up

I asked the user which websites were affected.

The user identified:

- Google Drive (`drive.google.com`)
- An internal web-based scheduling portal
- YouTube (`youtube.com`)

### Initial Symptoms

- Windows displayed an active network connection.
- Google Drive and YouTube failed to load.
- Chrome indicated a possible firewall issue.
- ICMP connectivity was successful.
- DNS resolution was successful.
- TCP connectivity to the tested web service failed.

### Root Cause

An enabled Windows Defender Firewall outbound rule named `INC036-Lab-Policy` was blocking TCP traffic on remote ports 80 and 443.

### Resolution

Disabled the offending firewall rule and confirmed that Google Drive and YouTube became accessible.

## 6. TCP Connectivity Investigation

### Step 5 — Test HTTP Connectivity

Command executed:

```powershell
Test-NetConnection drive.google.com -Port 80
```

Relevant output:

```text
WARNING: TCP connect to (172.217.75.139 : 80) failed
WARNING: TCP connect to (172.217.75.100 : 80) failed
WARNING: TCP connect to (172.217.75.138 : 80) failed
WARNING: TCP connect to (172.217.75.113 : 80) failed
WARNING: TCP connect to (172.217.75.101 : 80) failed
WARNING: TCP connect to (172.217.75.102 : 80) failed

ComputerName      : drive.google.com
RemoteAddress     : 172.217.75.139
RemotePort        : 80
InterfaceAlias    : Ethernet0
SourceAddress     : 192.168.254.78
PingSucceeded     : True
PingReplyDetails  : 11 ms
TcpTestSucceeded  : False
```

### Analysis

This test provided an important distinction:

```text
PingSucceeded    : True
TcpTestSucceeded : False
```

The workstation could reach the destination using ICMP but could not establish a TCP connection on port 80.

Possible explanations included:

- A local firewall restriction.
- An upstream firewall restriction.
- A destination service not listening on the tested port.
- A network security policy.
- Other TCP connectivity problems.

The browser's firewall-related error increased suspicion of a local firewall restriction.

A failed TCP test alone does not conclusively identify the firewall as the cause.

### Step 6 — Test Local Loopback TCP Connectivity

Command executed:

```powershell
Test-NetConnection 127.0.0.1 -Port 80
```

Output:

```text
WARNING: TCP connect to (127.0.0.1 : 80) failed

ComputerName      : 127.0.0.1
RemoteAddress     : 127.0.0.1
RemotePort        : 80
InterfaceAlias    : Loopback Pseudo-Interface 1
SourceAddress     : 127.0.0.1
PingSucceeded     : True
PingReplyDetails  : 0 ms
TcpTestSucceeded  : False
```

### Analysis

The loopback address responded to ICMP, but no TCP connection could be established on port 80.

This result was not conclusive evidence of a firewall problem.

A TCP connection to `127.0.0.1:80` requires a local service to be listening on that port. If no web server is running locally, the connection can fail even when the firewall is configured correctly.

**Lesson:** A TCP port test is most meaningful when the destination is expected to accept connections on that port.

## 9. Root Cause Analysis

### Confirmed Root Cause

The workstation had an enabled outbound Windows Defender Firewall rule:

```text
DisplayName : INC036-Lab-Policy
Direction   : Outbound
Action      : Block
Enabled     : True
Protocol    : TCP
RemotePort  : 80,443
```

The protocol and port configuration were known from the lab fault injection.

### Why Websites Failed

Most traditional web traffic uses:

| Protocol | Port | Purpose |
|---|---|---|
| HTTP | TCP 80 | Unencrypted web traffic |
| HTTPS | TCP 443 | Encrypted web traffic |
| QUIC / HTTP/3 | UDP 443 | Modern encrypted web transport |

The injected firewall rule blocked outbound TCP connections to remote ports 80 and 443.

This prevented TCP-based HTTP and HTTPS connections from being established.

### Why Ping Still Worked

`ping` uses ICMP rather than TCP.

The injected firewall rule specifically targeted TCP traffic, so ICMP packets were not blocked by that rule.

Therefore:

```text
ICMP Connectivity: Successful
DNS Resolution:    Successful
TCP Web Access:    Failed
```

### Why DNS Still Worked

DNS queries commonly use UDP port 53, with TCP port 53 used in certain situations.

The injected firewall rule targeted remote TCP ports 80 and 443, not DNS port 53.

The workstation could therefore continue resolving hostnames.

### Important Distinction

A successful ping does not prove that web traffic is functioning.

Different protocols can be affected by different firewall rules.

## 10. Remediation

### Corrective Action

Disabled the offending Windows Firewall rule.

The recommended PowerShell command was:

```powershell
Disable-NetFirewallRule -DisplayName "INC036-Lab-Policy"
```

The technician confirmed that the firewall restriction was removed or disabled successfully.

The exact remediation command output was not captured in the provided session.

### Why This Was Appropriate

The rule was a deliberately injected lab fault and was not part of a legitimate organizational security policy.

Disabling the specific rule addressed the problem without disabling Windows Defender Firewall globally.

### Production Environment Considerations

In a real enterprise environment, a technician should:

1. Confirm the rule's purpose and source.
2. Determine whether it was deployed through Group Policy, Intune, or another security platform.
3. Review relevant security policies and change-management requirements.
4. Obtain authorization if required.
5. Modify only the affected rule.
6. Verify that the change does not weaken necessary security controls.

**Do not disable the entire firewall simply because a website is inaccessible.**

## 14. Lessons Learned

### Technical Lessons

1. Successful ICMP connectivity does not guarantee successful TCP connectivity.
2. DNS resolution can work even when HTTP and HTTPS traffic are blocked.
3. Windows Defender Firewall supports outbound rules that restrict specific protocols and ports.
4. `Test-NetConnection` can test connectivity to a specified TCP port.
5. `Get-NetFirewallRule` can identify enabled firewall rules and their actions.
6. `Get-NetFirewallPortFilter` can reveal protocol and port restrictions associated with a firewall rule.
7. Firewall rules should be inspected and modified individually rather than disabling the entire firewall.
8. A failed connection to `127.0.0.1:80` does not prove a firewall problem unless a local service is expected to listen on that port.

### Troubleshooting Lessons

This incident reinforced the importance of distinguishing between different types of network connectivity.

My initial checks showed that:

- IPv4 addressing was valid.
- DHCP was functioning.
- DNS resolution succeeded.
- The default gateway was configured.
- External ICMP traffic succeeded.

However, websites still failed to load.

After asking the user which websites were affected, I tested TCP connectivity and inspected the firewall configuration.

This narrowed the issue to a specific outbound blocking rule.

### PowerShell Lessons

I successfully used:

```powershell
Get-NetFirewallRule
```

to identify an enabled outbound block rule.

I also learned that firewall rule display names must be referenced accurately.

Two inspection commands failed because I used incorrect rule names.

The correct troubleshooting process is to enumerate the existing rules first, identify the exact display name, and then inspect the matching rule.
