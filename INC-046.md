## 1. Ticket Summary

A departmental shared folder was provisioned on a Windows Server 2022 domain controller and made accessible to a domain-joined Windows 11 workstation.

The objective was to simulate a common IT service request in which a department requires centralized file storage accessible to authorized employees over the local network.

The configuration involved:

- Verifying Active Directory and SMB services.
- Diagnosing a server hostname resolution issue.
- Confirming TCP 445 connectivity.
- Creating a dedicated shared directory.
- Creating a sample document.
- Publishing the directory as an SMB share.
- Assigning domain-based share permissions.
- Inspecting the SMB share configuration.
- Accessing the share from a domain-joined workstation.
- Verifying successful remote file access.

**Outcome:** The departmental SMB share was created successfully, and the domain user `ADEN\jsmith` accessed and opened `Welcome.txt` from COMP01.

### Finding — VMware Name vs. Windows Hostname

The virtual machine was labeled `DC01` in VMware Workstation.

However, its actual Windows hostname was:


A VMware VM display name does not automatically become the Windows computer hostname or a DNS alias.

This discrepancy was a plausible explanation for the failed resolution of `DC01`.

The DNS records were not fully investigated during this ticket.

**Future improvement:** Verify the server's registered DNS records and consider using a consistent hostname or properly configured DNS alias.

## 7. Publish Folder as an SMB Share

### 7.1 Create the Share

On DC01:

```powershell
New-SmbShare `
    -Name "Department" `
    -Path "C:\LabShares\Department" `
    -ReadAccess "aden\Domain Users" `
    -FullAccess "aden\Domain Admins"
```

**Observed output:**

```text
Name        ScopeName Path
----        --------- ----
Department  *         C:\LabShares\Department
```

The SMB share was created successfully.

### Parameter Explanation

| Parameter | Function |
|---|---|
| `-Name` | Defines the SMB share name |
| `-Path` | Specifies the local directory being shared |
| `-ReadAccess` | Grants read-level share permissions |
| `-FullAccess` | Grants full share permissions |

### Permissions Assigned

| Security Principal | SMB Share Permission |
|---|---|
| ADEN\Domain Admins | Full |
| ADEN\Domain Users | Read |

The configuration allowed domain users to access the shared folder with read-only SMB permissions.

Domain administrators received Full share permissions.

**Important:** SMB share permissions do not replace NTFS permissions. Both permission layers must permit an operation for it to succeed.

## 10. Understanding UNC Paths

A UNC (Universal Naming Convention) path identifies a shared resource on another computer.

General format:

```text
\\SERVER\SHARE
```

Optional file path:

```text
\\SERVER\SHARE\FOLDER\FILE
```

Example from this lab:

```text
\\192.168.17.128\Department\Welcome.txt
```

### Components

| Component | Meaning |
|---|---|
| `\\` | Begins a UNC network path |
| `192.168.17.128` | SMB server |
| `Department` | Published share name |
| `Welcome.txt` | File inside the share |

A UNC path can use a hostname or IP address.

In a properly configured Active Directory environment, a DNS hostname is usually preferable for maintainability.

**Note:** Accessing a UNC path by IP may affect authentication behavior in some environments, particularly those requiring Kerberos. Use an appropriately configured server name when Kerberos authentication is required.

## 12. SMB Share Permissions vs. NTFS Permissions

Windows file sharing uses two permission layers.

### SMB Share Permissions

Apply when users access a folder over the network through SMB.

Common levels:

- Read
- Change
- Full

### NTFS Permissions

Apply to files and directories stored on NTFS volumes.

Common permissions include:

- Read
- Read & Execute
- Write
- Modify
- Full Control

### Effective Access

For network access, both SMB share permissions and NTFS permissions must allow the requested operation.

Example:

| Share Permission | NTFS Permission | Effective Network Access |
|---|---|---|
| Read | Modify | Read |
| Change | Modify | Modify-level operations |
| Full | Read | Read |
| Full | Modify | Modify-level operations |

These examples assume no additional restrictions or explicit Deny entries.

**Key principle:** Granting Full access at the share level does not override restrictive NTFS permissions.

### Recommended Administrative Practice

For a production departmental share:

1. Create dedicated AD security groups.
2. Assign permissions to groups rather than individual users.
3. Apply least-privilege access.
4. Use NTFS permissions to control folder and file access.
5. Verify effective access using a standard user account.
6. Document authorized access changes.

## 13. Troubleshooting Reference

### Problem: Shared Folder Cannot Be Found

Check:

```powershell
Test-NetConnection SERVER_IP -Port 445
```

Verify the share exists:

```powershell
Get-SmbShare
```

Check hostname resolution:

```powershell
Resolve-DnsName SERVER_HOSTNAME
```

### Problem: Access Denied

Inspect SMB permissions:

```powershell
Get-SmbShareAccess -Name "Department"
```

Inspect NTFS permissions:

```powershell
(Get-Acl "C:\LabShares\Department").Access
```

Check the current identity:

```powershell
whoami
```

Check group membership:

```powershell
whoami /groups
```

Determine whether the user has the required access through both permission layers.

### Problem: Shared Folder Opens but Files Cannot Be Modified

Possible causes include:

- Read-only SMB share permissions.
- Insufficient NTFS permissions.
- Missing AD group membership.
- Explicit Deny entries.
- File-level permissions.
- File locks or application restrictions.

Investigate the specific denied operation before modifying access.

### Problem: Server Reachable by IP but Not Hostname

Inspect DNS:

```powershell
ipconfig /all
```

```powershell
Resolve-DnsName SERVER_HOSTNAME
```

Confirm the correct DNS server and registered hostname.

Do not assume a VMware VM display name is a valid Windows hostname.

## 14. Security and Production Considerations

This exercise was performed in an isolated homelab.

For real-world environments:

- Avoid hosting general-purpose departmental shares on domain controllers when dedicated file servers are available.
- Do not grant unnecessary access to broad security groups.
- Avoid using Domain Admins for routine file access.
- Prefer dedicated resource-specific AD groups.
- Apply least privilege.
- Review NTFS inheritance before modifying permissions.
- Avoid exposing SMB directly to the public internet.
- Follow organizational approval procedures for access changes.
- Verify access with a standard user account.

The broad `Domain Users` permission used in this lab was intentionally selected for a simple read-only access demonstration.
