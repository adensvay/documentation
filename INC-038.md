
# INC-038 — Windows Event Viewer and Service Diagnostics

**Date:** October 27, 2026  
**Category:** Windows Endpoint Support / Event Log Investigation  
**Environment:** Windows 11 — COMP02  
**Tools:** Event Viewer, PowerShell, Windows Services  
**Status:** Completed — Guided Diagnostic Exercise

---

## 1. Objective

Develop foundational troubleshooting skills using Windows Event Viewer and PowerShell.

Training objectives:

- Navigate Windows Application and System event logs.
- Filter events by Event ID, source, and severity.
- Interpret Service Control Manager events.
- Retrieve Windows events using PowerShell.
- Correlate event timestamps with system changes.
- Distinguish informational events from actual failures.

This exercise was performed in a controlled Windows 11 virtual machine.

---

## 2. Initial Scenario

A simulated Finance Reporting Tool was created to reproduce an application startup failure.

The intended troubleshooting workflow was:

1. Launch the application.
2. Observe the failure.
3. Locate its error in Event Viewer.
4. Identify the cause.
5. Remediate and verify.

However, the simulated application encountered unintended setup issues before the intended application error could be logged.

The exercise was therefore changed to investigating real Windows service events.

---

## 3. Initial Application Investigation

### Observed Symptoms

The Finance Reporting Tool shortcut launched a PowerShell-based application that immediately disappeared.

Initially, this appeared consistent with an application crash.

### Event Viewer Investigation

Opened Event Viewer:

```text
eventvwr.msc
```

Navigated to:

```text
Windows Logs > Application
```

Filtered for Event ID `1038`.

Two matching events were found, but their source was `MsiInstaller`, associated with VMware Tools.

Neither event belonged to the Finance Reporting Tool.

### Lesson

Event IDs are not globally unique.

Different event providers may use the same numeric Event ID.

An event must be evaluated using:

- Log name
- Event source/provider
- Event ID
- Timestamp
- Event message

## 4. PowerShell Execution Policy Investigation

Attempted to run the application directly:

```powershell
& "C:\ProgramData\FinanceReporting\FinanceReporting.ps1"
```

### Result

```text
File cannot be loaded because running scripts is
disabled on this system.

PSSecurityException
FullyQualifiedErrorId : UnauthorizedAccess
```

### Execution Policy Inspection

Executed:

```powershell
Get-ExecutionPolicy -List
```

Observed:

```text
Scope          ExecutionPolicy
-----          ---------------
MachinePolicy  Undefined
UserPolicy     Undefined
Process        Undefined
CurrentUser    Undefined
LocalMachine   Undefined
```

The effective policy prevented direct execution of the script.

### Temporary Execution Attempt

Executed:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\ProgramData\FinanceReporting\FinanceReporting.ps1"
```

The application reached its error-handling code but prompted for a missing `Write-EventLog` parameter.

Inspection revealed that the generated script contained a malformed multiline logging command.

The custom application scenario was abandoned rather than introducing additional changes unrelated to the Event Viewer learning objectives.

### Lesson

An application may fail before generating its expected event log entry.

When logs are missing, running the application directly can expose errors hidden by a shortcut or graphical interface.

## 5. Windows Time Service Investigation

The replacement exercise used the built-in Windows Time service.

### Initial Service Inspection

Executed:

```powershell
Get-Service W32Time
```

Observed:

```text
Status   Name      DisplayName
------   ----      -----------
Stopped  W32Time   Windows Time
```

### Service Operations

Executed:

```powershell
Stop-Service W32Time
Start-Sleep -Seconds 2
Start-Service W32Time
```

### Verification

Executed:

```powershell
Get-Service W32Time
```

Observed:

```text
Status   Name      DisplayName
------   ----      -----------
Running  W32Time   Windows Time
```

The service was running after the operation.

The initial stopped state was not independently established as a fault.

## 6. Event Viewer — System Log

Opened:

```text
Event Viewer > Windows Logs > System
```

Investigated Service Control Manager events.

### Event ID 7036

Event ID `7036` commonly records a Windows service entering a running or stopped state.

Filtered the System log for:

```text
7036
```

### Result

```text
Number of matching events: 0
```

Also attempted to retrieve Windows Time events using PowerShell:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'System'
    Id = 7036
    StartTime = (Get-Date).AddMinutes(-30)
} -ErrorAction SilentlyContinue |
Where-Object {
    $_.Message -like '*Windows Time*'
} |
Select-Object TimeCreated, Id, ProviderName, Message
```

No matching events were returned.

### Finding

The Windows Time service was confirmed running through PowerShell, but the expected Event ID 7036 was not present.

This demonstrated that a successful service operation does not guarantee that a particular event will appear in the available logs.

---

## 7. Event ID 7040 Investigation

While examining the System log, identified events from:

```text
Source: Service Control Manager
Event ID: 7040
Level: Information
```

Event ID `7040` records changes to a service's startup configuration.

One event reported:

```text
The start type of the Background Intelligent
Transfer Service service was changed from
demand start to auto start.
```

This event referred to BITS, not Windows Time.

### Interpretation

Event ID `7040` documents startup configuration changes.

It does not establish that a service crashed or unexpectedly stopped.

---

## 8. Retrieving Events with PowerShell

Executed:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'System'
    Id = 7040
} -MaxEvents 5 |
Select-Object TimeCreated, Id, ProviderName, Message |
Format-List
```

### Results

| Timestamp | Service | Recorded Change |
|---|---|---|
| 12:12:39 PM | Windows Search | Disabled → Automatic |
| 12:46:31 PM | BITS | Manual → Automatic |
| 12:48:36 PM | BITS | Automatic → Manual |
| 1:01:16 PM | BITS | Manual → Automatic |
| 1:03:20 PM | BITS | Automatic → Manual |

All events were recorded on October 27, 2026.

### Important Finding

The Windows Search event at 12:12:39 PM corresponded to the remediation performed during INC-037.

During that earlier incident, the Windows Search service startup type was changed from Disabled to Automatic.

The Event Viewer record provided independent historical evidence of that configuration change.

### BITS Findings

Several BITS startup configuration changes were recorded.

These events did not independently establish a malfunction.

No corrective action was taken against BITS.

## 9. Event ID Reference

| Event ID | Source | Meaning |
|---|---|---|
| 7036 | Service Control Manager | Service entered a running or stopped state |
| 7040 | Service Control Manager | Service startup configuration changed |
| 1038 | Provider-dependent | Meaning depends on the event source |

### Key Distinction

**Service status** describes whether a service is currently running.

**Startup type** describes how Windows is configured to start that service.

These are separate properties and may generate different events.

## 11. Lessons Learned

### Event Viewer Is an Evidence Source

Event Viewer records Windows and application activity, but individual events must be interpreted in context.

An informational event does not necessarily indicate a problem.

### Correlate Multiple Evidence Sources

Use Event Viewer alongside:

```powershell
Get-Service
Get-WinEvent
Get-ExecutionPolicy
```

The combination of current system state and historical logs provides a stronger basis for troubleshooting.

### Investigate Missing Events

If an expected event is absent:

1. Verify the correct event log.
2. Check timestamps.
3. Confirm the event source.
4. Inspect available event levels.
5. Verify the operation independently.
6. Avoid assuming an event must exist.

### Prefer Reliable Lab Scenarios

A training exercise should reproduce the intended symptom without introducing unrelated setup problems.

This incident reinforced the importance of validating fault injections before relying on their results.
