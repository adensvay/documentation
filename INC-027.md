# Reusable Guide — Deploying Open-Source Software Through Intune

## Phase 1 — Obtain a Trusted Installer

### Step 1: Identify the Official Publisher

Before downloading an application, verify:

- The software's official website.
- The publisher's identity.
- Whether the application is maintained.
- Its license and permitted use.
- Compatibility with the organization's operating systems.
- Whether the installer is signed or offers a published checksum.

For this deployment, the official 7-Zip website was used:

https://www.7-zip.org/

The Microsoft Win32 Content Prep Tool was obtained from Microsoft's GitHub repository:

https://github.com/microsoft/Microsoft-Win32-Content-Prep-Tool

### Important Security Consideration

Open-source software is not automatically safe merely because its source code is publicly available.

Enterprise administrators should evaluate:

- Repository authenticity.
- Maintainer reputation.
- Release history.
- Installer provenance.
- Digital signatures or checksums.
- Licensing requirements.
- Known security vulnerabilities.

Only trusted and approved software should be deployed to managed endpoints.

## Phase 2 — Prepare the Installer

### Step 2: Create Packaging Directories

A reusable folder structure is:

```text
C:\IntunePackages\
│
├── 7Zip\
│   └── 7z2605-x64.exe
│
├── Tools\
│   └── IntuneWinAppUtil.exe
│
└── Output\
```

Create the directories using PowerShell:

```powershell
New-Item -ItemType Directory -Force -Path `
    "C:\IntunePackages\7Zip", `
    "C:\IntunePackages\Tools", `
    "C:\IntunePackages\Output"
```

Place the downloaded installer inside the `7Zip` folder.

Place the Microsoft packaging utility inside the `Tools` folder.

### Packaging Best Practices

- Keep each application's source files in a dedicated folder.
- Do not include unrelated files.
- Do not place the packaging utility inside the source directory.
- Keep the output directory separate from the source directory.
- Prefer local directories outside OneDrive or other synchronized folders.

A synchronized Desktop folder can work, but local packaging directories reduce potential file-locking and synchronization issues.

## Phase 3 — Package the Application

### Step 3: Launch the Content Prep Tool

Open PowerShell:

```powershell
& "C:\IntunePackages\Tools\IntuneWinAppUtil.exe"
```

The tool prompts for the application source folder, setup file, and output directory.

Example:

```text
Please specify the source folder:
C:\IntunePackages\7Zip

Please specify the setup file:
7z2605-x64.exe

Please specify the output folder:
C:\IntunePackages\Output
```

If prompted for a catalog folder, enter:

```text
N
```

### Expected Output

```text
C:\IntunePackages\Output\7z2605-x64.intunewin
```

Verify the package:

```powershell
Get-ChildItem "C:\IntunePackages\Output" |
    Select-Object Name,Length,LastWriteTime
```

### Technical Explanation

The Microsoft Win32 Content Prep Tool packages the application installer and required supporting files into an encrypted `.intunewin` file.

It does not convert the original EXE into another executable.

The package allows Intune to distribute the installation content to managed Windows endpoints.

The installation behavior is configured separately in Intune.

## Phase 6 — Configure Installation Commands

### Step 6: Program Settings

Because this deployment uses the official 7-Zip EXE installer, the silent installation command is:

```cmd
7z2605-x64.exe /S
```

The `/S` switch instructs the installer to run silently.

### Uninstall Command

For a standard 64-bit installation, a candidate uninstall command is:

```cmd
"%ProgramFiles%\7-Zip\Uninstall.exe" /S
```

Verify the actual uninstall executable and its supported switches on a test machine before relying on this command for production removal.

### Install Behavior

```text
Install behavior: System
```

System installation allows Intune to install the application in the device context without requiring the signed-in employee to have local administrator privileges.

### Why Silent Installation Matters

Enterprise software deployment should generally avoid requiring the user to interact with installation prompts.

Silent installation supports:

- Automated provisioning.
- Consistent installations.
- Remote software management.
- Large-scale deployment.
- Reduced end-user interruption.

| Additional requirements | None |

The installer was intended for x64 Windows devices.

### Requirements vs. Detection Rules

**Requirements** determine whether an application is eligible to install on a device.

**Detection rules** determine whether the application is already installed.

This distinction is important when diagnosing deployment failures.

For example:

- An architecture mismatch can cause an application to be marked not applicable.
- An incorrect detection rule can prevent Intune from recognizing a successful installation.

## Phase 8 — Configure Detection Rules

### Step 8: Select Detection Method

Choose:

```text
Manually configure detection rules
```

Add a file detection rule.

| Setting | Value |
|---|---|
| Rule type | File |
| Path | C:\Program Files\7-Zip |
| File or folder | 7z.exe |
| Detection method | File or folder exists |
| Associated with a 32-bit app on 64-bit clients | No |

### Expected Detection Target

```text
C:\Program Files\7-Zip\7z.exe
```

### How Detection Works

After installation, Intune evaluates the configured detection rule.

If the executable exists at the expected location, Intune can consider the application detected.

If the executable is missing, the application is not detected.

### Production Consideration

File-existence detection is useful for basic deployments but does not guarantee that the correct application version is installed.

For production application upgrades, consider:

- File version detection.
- MSI product-code detection when applicable.
- Registry-based detection.
- Custom PowerShell detection scripts.

## Phase 10 — Assign the Application

### Step 11: Select a Test Audience

A limited test assignment was used rather than deploying to all organizational users.

Intune supports two common assignment strategies.

| Assignment type | Behavior |
|---|---|
| User group | Targets eligible managed devices associated with assigned users |
| Device group | Targets specific managed devices regardless of signed-in user |

For predictable testing, a dedicated device pilot group is recommended.

Example:

```text
SG-Intune-App-Pilot
```

Member:

```text
COMP01
```

### Recommended Assignment

```text
Assignment type: Required
Target: SG-Intune-App-Pilot
```

A Required assignment directs Intune to install the application automatically on eligible targeted devices.

An Available assignment generally allows the user to initiate installation through Company Portal.

### Actual Lab Note

The deployment was observed under a working test user's account, and application files were subsequently confirmed on COMP01.

The exact final assignment configuration was not independently captured in the ticket evidence.

### Deployment Best Practice

For production environments:

1. Test on a small pilot group.
2. Verify installation and application functionality.
3. Review failures and compatibility issues.
4. Expand to additional devices.
5. Monitor the broader rollout.

Avoid targeting all devices before validating a new application package.

# Monitoring and Troubleshooting Guide

## 1. Monitor Deployment Status in Intune

Navigate to:

**Intune → Apps → Windows → Windows apps → 7-Zip → Monitor**

Review:

- Device install status.
- User install status.
- Installation errors.
- Applicable and non-applicable devices.

### Common Statuses

| Status | Meaning |
|---|---|
| Installed | Application successfully detected |
| Failed | Installation or detection failed |
| Install pending | Installation not yet completed |
| Not installed | Application not detected |
| Not applicable | Device does not satisfy applicable requirements |

Application upload completion is not the same as endpoint installation completion.

---

## 2. Locate Intune Management Extension Logs

On the managed Windows device, navigate to:

```text
C:\ProgramData\Microsoft\IntuneManagementExtension\Logs
```

`ProgramData` is a hidden Windows folder.

To display it:

**File Explorer → View → Show → Hidden items**

Alternatively, paste the full path into the File Explorer address bar.

### Important Log Files

| Log | Purpose |
|---|---|
| IntuneManagementExtension.log | General management extension processing |
| AppWorkload.log | Win32 application processing and installation |
| AppActionProcessor.log | Application detection and applicability |
| AgentExecutor.log | PowerShell script execution through the extension |

### Read Recent Application Logs

```powershell
Get-Content `
    "C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AppWorkload.log" `
    -Tail 80
```

Search for relevant entries:

```powershell
Select-String `
    -Path "C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AppWorkload.log" `
    -Pattern "install","detection","error" |
    Select-Object -Last 30
```

Application activity may be recorded under an application ID rather than its friendly name.

### Check Whether the Extension Is Installed

```powershell
Get-Service -Name IntuneManagementExtension `
    -ErrorAction SilentlyContinue
```

Check for the log directory:

```powershell
Test-Path `
    "C:\ProgramData\Microsoft\IntuneManagementExtension\Logs"
```

If the directory is absent, investigate whether the Intune Management Extension has been installed and whether Win32 app policy has reached the device.

## 3. Common Win32 Deployment Failures

### Application Never Installs

Possible causes:

- Device not targeted by the assignment.
- User has no eligible managed device.
- Device has not checked in.
- Operating system requirements not satisfied.
- Intune Management Extension not processing the app.
- Conflicting or incorrect assignment configuration.

### Application Installs but Intune Reports Failure

Possible causes:

- Incorrect detection path.
- Detection rule checks the wrong executable.
- Installation command returns an unexpected exit code.
- Application installed into a different directory.
- Installation completes but detection runs before the expected file becomes available.

### Application Reports Not Applicable

Possible causes:

- Unsupported processor architecture.
- Operating system version below minimum.
- Additional requirement rules not satisfied.

### Application Fails During Installation

Possible causes:

- Incorrect silent installation switches.
- Missing installation files.
- Installer requires a dependency.
- Installation context is inappropriate.
- Application conflicts with an existing version.

### Recommended Troubleshooting Order

1. Confirm the device is managed and checking in.
2. Confirm the application assignment.
3. Confirm device eligibility.
4. Review Intune installation status.
5. Inspect Intune Management Extension logs.
6. Verify the installation command.
7. Verify the detection rule.
8. Check the actual endpoint installation.
9. Remediate the identified root cause.
10. Recheck deployment status.

## 13. Lessons Learned

### 1. Packaging and Installation Are Different Operations

The `.intunewin` package prepares application content for Intune distribution.

Installation commands determine how the software is installed on the endpoint.

### 2. Open-Source Tools Can Be Valuable in Enterprise IT

The Microsoft Win32 Content Prep Tool demonstrates how publicly available tooling can support enterprise workflows.

However, software must still be evaluated for trust, licensing, maintenance, and security.

### 3. Detection Rules Are Essential

Intune needs a reliable way to determine whether an application is installed.

Poor detection configuration can cause incorrect deployment reporting.

### 4. Device Assignment Is Not the Same as User Assignment

User assignments require eligible managed devices associated with targeted users.

Device assignments can provide a simpler test scope in a small homelab.

### 5. Silent Installation Enables Scalable Deployment

Automated installation reduces end-user interaction and supports centralized endpoint administration.

### 6. Upload Success Does Not Prove Installation Success

The Intune upload notification confirms that application content was uploaded.

Device installation must be verified separately.

### 7. Logs Are a Future Troubleshooting Priority

The next learning objective is to inspect Intune Management Extension logs and correlate installation events with Intune reporting.
