
# INC-026 — Privileged Cloud Identity Offboarding

**Category:** Identity & Access Management (IAM) / Account Offboarding  
**Priority:** P3 — Administrative Service Request  
**Environment:** Microsoft Entra ID, Microsoft Graph PowerShell, Active Directory, Entra Connect Sync  
**Date:** October 20–21, 2026  
**Status:** Completed — cloud account deleted; additional production-grade checks documented  
**Documentation:** Anonymized homelab incident report and offboarding runbook

---

## 1. Incident Summary

During a review of Microsoft Entra ID users, two identities were identified with the same display name.

One identity originated from on-premises Active Directory and synchronized to Entra ID. The other was a cloud-managed account with a `#EXT#` user principal name (UPN).

Further investigation revealed that the cloud-managed identity held the **Global Administrator** directory role.

The objective was to retire the redundant cloud-managed identity without disrupting the legitimate hybrid account or losing administrative access to the tenant.

### Business Requirements

- Identify the source of authority for each account.
- Determine which account should be retained.
- Review administrative roles and access dependencies.
- Establish and verify replacement Global Administrator access.
- Deprovision the redundant cloud-managed account.
- Verify the account's deletion.
- Preserve administrative continuity.

**Scope:** This incident concerned duplicate identity cleanup and privileged account retirement. It was not the termination of an employee.

## 3. Investigation and Troubleshooting

### Step 1 — Connect to Microsoft Graph

**Command executed:**

```powershell
Connect-MgGraph -Scopes `
    "User.Read.All", `
    "Directory.Read.All"
```

**Result:** Successfully authenticated to Microsoft Graph using delegated permissions.

### Step 2 — Identify Duplicate-Looking Accounts

**Command executed (anonymized):**

```powershell
Get-MgUser -All `
    -Filter "displayName eq 'Example Employee'" `
    -Property Id,DisplayName,UserPrincipalName,AccountEnabled,OnPremisesSyncEnabled |
    Select-Object DisplayName,UserPrincipalName,
                  AccountEnabled,OnPremisesSyncEnabled,Id |
    Format-List
```

**Findings:**

Two user objects shared the same display name but had different UPNs and object IDs.

- Account A was cloud-managed.
- Account B was synchronized from on-premises AD.
- Both accounts were enabled.

**Analysis:**

Matching display names are insufficient evidence that accounts are duplicates. Identity source, account ownership, roles, and dependencies must be investigated before deprovisioning.

### Step 3 — Inspect Cloud Account Type

**Command executed (anonymized):**

```powershell
$target = Get-MgUser `
    -UserId "<CLOUD_ACCOUNT_OBJECT_ID>" `
    -Property Id,DisplayName,UserPrincipalName,UserType,AccountEnabled

$target |
    Select-Object DisplayName,UserPrincipalName,UserType,AccountEnabled
```

**Observed result:**

```text
DisplayName    : [REDACTED]
UserPrincipalName : [external_identity]#EXT#@[tenant].onmicrosoft.com
UserType       : Member
AccountEnabled : True
```

**Analysis:**

The `#EXT#` UPN pattern commonly indicates an identity originally associated with an external email address.

However, the account was classified as `Member`, not `Guest`.

The naming convention alone does not establish the account's current classification or privileges.

### Step 4 — Inspect Directory Roles and Group Memberships

**Command executed:**

```powershell
Get-MgUserMemberOf -UserId $target.Id -All |
    ForEach-Object {
        [PSCustomObject]@{
            ObjectType = $_.AdditionalProperties['@odata.type']
            Name       = $_.AdditionalProperties['displayName']
            Id         = $_.Id
        }
    } |
    Format-Table -AutoSize
```

**Observed findings:**

| Object type | Membership |
|---|---|
| Directory role | Global Administrator |
| Group | Default Directory |

**Analysis:**

The proposed retirement target possessed elevated administrative privileges.

Deleting this identity without establishing another working Global Administrator could have resulted in tenant administrative lockout.

This changed the ticket from routine duplicate-account cleanup into a **privileged identity retirement procedure**.

Direct membership inspection does not replace a complete review of effective permissions, Privileged Identity Management assignments, or application dependencies.

### Step 5 — Inspect Microsoft 365 Licensing

**Command executed:**

```powershell
Get-MgUserLicenseDetail -UserId $target.Id |
    Select-Object SkuPartNumber,SkuId
```

**Observed result:** No license details were returned.

**Limitation:** The absence of license assignments does not prove that an account has no application ownership, administrative dependencies, or associated data.

### Step 6 — Verify the Retained Hybrid Identity

**Command executed (anonymized):**

```powershell
Get-MgUser -UserId "<RETAINED_USER_UPN>" `
    -Property DisplayName,UserPrincipalName,
              AccountEnabled,OnPremisesSyncEnabled |
    Select-Object DisplayName,UserPrincipalName,
                  AccountEnabled,OnPremisesSyncEnabled
```

**Observed result:**

```text
AccountEnabled        : True
OnPremisesSyncEnabled : True
```

The retained identity was enabled and synchronized from on-premises Active Directory before the deletion.

## 4. Administrative Continuity

Because the target account was a Global Administrator, replacement administrative access was required before deprovisioning.

### Actions Completed

1. Identified the target's Global Administrator role.
2. Assigned Global Administrator privileges to additional backup accounts.
3. Verified replacement administrative access.
4. Confirmed the target identity could be retired without intentionally removing the retained hybrid user.

The administrator migration was completed through Microsoft Entra ID.

### Security Considerations

For production environments:

- Maintain independently secured cloud-only emergency administrator accounts.
- Verify replacement administrators through separate authentication sessions.
- Avoid depending exclusively on synchronized AD identities for tenant recovery.
- Review app registrations, enterprise applications, automation, and ownership dependencies.
- Follow organizational approval and retention requirements.

**Important:** Global Administrator is a Microsoft Entra directory role, not an on-premises AD Domain Admin role.

---

## 5. Account Deprovisioning

### Action Performed

After establishing and verifying backup Global Administrators, the target cloud-managed account was deleted through the Microsoft Entra admin center.

### Verification

The deleted identity was observed under:

**Entra ID → Users → Deleted users**

This confirmed that the account was no longer present as an active Entra user and had entered the deleted-user lifecycle.

### Hybrid Synchronization Consideration

No Entra Connect synchronization was required for this cloud-managed account deletion.

The command:

```powershell
Start-ADSyncSyncCycle -PolicyType Delta
```

is used to initiate synchronization of eligible on-premises AD changes.

It does not need to be executed when deleting an independently cloud-managed Entra account.

# Standard Operating Procedure — Future Offboarding Incidents

The following procedure is a reusable guide for employee departures, duplicate-account retirement, and routine identity deprovisioning.

The exact actions depend on whether the identity is cloud-managed or synchronized from on-premises Active Directory.

## Phase 1 — Validate Authorization

Before modifying any account:

1. Confirm the request originated from an authorized HR representative, manager, or account owner.
2. Verify the employee's identity using unique identifiers.
3. Establish the effective offboarding date and time.
4. Determine whether the employee is leaving or whether only a redundant identity is being retired.
5. Identify any privileged, service, shared, or application dependencies.

Never rely solely on matching display names.

## Phase 2 — Determine the Source of Authority

Inspect the user in Entra ID:

```powershell
Get-MgUser -UserId "<USER_UPN>" `
    -Property DisplayName,UserPrincipalName,
              AccountEnabled,OnPremisesSyncEnabled |
    Select-Object DisplayName,UserPrincipalName,
                  AccountEnabled,OnPremisesSyncEnabled
```

### Decision

**If synchronized from AD:**

Perform authoritative account lifecycle changes in on-premises Active Directory, then synchronize and verify the cloud state.

**If cloud-managed:**

Perform the lifecycle change directly in Microsoft Entra ID.

This distinction prevents administrators from modifying the wrong identity system.

## Phase 3 — Document Existing Access

Before disabling or deleting an account, review:

- AD and Entra group memberships.
- Privileged directory roles.
- Microsoft 365 licensing.
- Enterprise application assignments.
- Mailbox and OneDrive ownership.
- SharePoint and Teams dependencies.
- Managed devices and application access.
- Business-critical automation or service dependencies.
- Retention, legal hold, and data preservation requirements.

For an on-premises AD account, group memberships can be inspected using:

```powershell
Get-ADPrincipalGroupMembership -Identity "<USERNAME>" |
    Select-Object Name,SamAccountName,GroupScope
```

For an Entra identity:

```powershell
Get-MgUserMemberOf -UserId "<USER_OBJECT_ID>" -All
```

Store sensitive exports securely. Do not commit actual employee records or access inventories to public GitHub repositories.

## Phase 4 — Disable Authentication

Disabling access is generally preferable to immediately deleting the identity.

### Option A — Hybrid-Synchronized Account

Preview the change:

```powershell
Disable-ADAccount -Identity "<USERNAME>" -WhatIf
```

Execute:

```powershell
Disable-ADAccount -Identity "<USERNAME>"
```

Verify:

```powershell
Get-ADUser -Identity "<USERNAME>" -Properties Enabled |
    Select-Object Name,SamAccountName,Enabled
```

Expected:

```text
Enabled : False
```

Initiate a delta sync from the Entra Connect server:

```powershell
Start-ADSyncSyncCycle -PolicyType Delta
```

Then verify the corresponding Entra identity is disabled.

### Option B — Cloud-Managed Account

Connect to Microsoft Graph with appropriate permissions:

```powershell
Connect-MgGraph -Scopes "User.ReadWrite.All"
```

Identify the target by its exact object ID:

```powershell
$targetId = "<CLOUD_USER_OBJECT_ID>"

Get-MgUser -UserId $targetId `
    -Property DisplayName,UserPrincipalName,AccountEnabled |
    Select-Object DisplayName,UserPrincipalName,AccountEnabled
```

After authorization and identity confirmation:

```powershell
Update-MgUser -UserId $targetId -AccountEnabled:$false
```

Verify:

```powershell
Get-MgUser -UserId $targetId `
    -Property DisplayName,UserPrincipalName,AccountEnabled |
    Select-Object DisplayName,UserPrincipalName,AccountEnabled
```

Expected:

```text
AccountEnabled : False
```

**PowerShell lesson:** `Disable-ADAccount` supports `-WhatIf`. Microsoft Graph's `Update-MgUser` does not provide the same native preview behavior. Perform an explicit read-only target check before executing Graph changes.

## Phase 5 — Revoke Active Cloud Sessions

Blocking sign-in prevents new authentication but does not guarantee immediate termination of all existing sessions.

With the appropriate Graph permissions and administrator role:

```powershell
Connect-MgGraph -Scopes "User.RevokeSessions.All"

Revoke-MgUserSignInSession -UserId "<USER_OBJECT_ID>"
```

This requests invalidation of refresh tokens and sign-in session cookies.

Existing access tokens may remain valid until they expire.

For urgent security incidents, follow the organization's incident-response procedures rather than assuming session revocation takes effect instantly.

## Phase 6 — Review Data and Access Cleanup

Once authentication has been disabled:

1. Preserve or transfer required mailbox and OneDrive data.
2. Reassign business-critical application ownership.
3. Review group memberships and application assignments.
4. Remove unnecessary privileged roles.
5. Review licenses only after considering mailbox and data retention consequences.
6. Address managed devices, credentials, and organizational assets.
7. Record outstanding actions requiring approval.

For duplicate-account cleanup, do not automatically transfer all permissions to the retained account.

Only approved, necessary access should be preserved.

## Phase 7 — Delete the Account

Delete the account only after:

- Authorization is confirmed.
- Administrative continuity is protected.
- Data preservation and retention requirements are addressed.
- Dependencies have been reviewed.
- The organization's deletion policy permits removal.

### Cloud-Managed Users

Delete the account through the Entra admin center or an authorized Graph operation.

Deleted users are generally recoverable for approximately 30 days, subject to the relevant Microsoft identity lifecycle behavior.

### Hybrid Users

For synchronized identities, deletion should be handled through the authoritative on-premises directory and allowed to synchronize.

Do not assume that deleting only the Entra representation is the correct permanent removal procedure.

**Permanent deletion should not be the default first step.**

## Phase 8 — Verify and Close

Before closing the ticket, verify:

| Control | Expected outcome |
|---|---|
| Target identity | Disabled or deleted as approved |
| Cloud state | Matches intended account lifecycle |
| Session revocation | Completed or documented as blocked |
| Privileged roles | Appropriate administrators remain |
| Retained identity | Unaffected and functional |
| Group/application access | Reviewed and updated |
| Business data | Preserved or transferred where required |
| Licensing | Reviewed according to retention policy |
| Documentation | Commands, evidence, approvals, exceptions recorded |

### Reference Verification Commands

Verify that a deleted cloud user is no longer active:

```powershell
Get-MgUser -UserId "<DELETED_USER_OBJECT_ID>"
```

Check the deleted-user object:

```powershell
Get-MgDirectoryDeletedItemAsUser `
    -DirectoryObjectId "<DELETED_USER_OBJECT_ID>" |
    Select-Object DisplayName,UserPrincipalName,Id
```

Confirm a retained identity remains enabled:

```powershell
Get-MgUser -UserId "<RETAINED_USER_UPN>" `
    -Property AccountEnabled,OnPremisesSyncEnabled |
    Select-Object AccountEnabled,OnPremisesSyncEnabled
```

These are reference commands and were not shown as executed during INC-026.

## 6. Lessons Learned

### 1. Duplicate Names Require Investigation

Two accounts with the same display name may serve different purposes.

Object IDs, UPNs, synchronization state, and directory roles provide more reliable evidence.

### 2. Privileged Accounts Require Additional Safeguards

The retirement target held Global Administrator privileges.

Administrative continuity had to be established before deleting it.

### 3. Source of Authority Determines the Workflow

Hybrid-synchronized users are managed primarily through AD for synchronized identity attributes.

Cloud-managed users are managed directly in Entra ID.

### 4. `#EXT#` Does Not Necessarily Mean Guest

An external-style UPN can belong to an account whose current `UserType` is `Member`.

Always inspect actual identity attributes.

### 5. Account Deletion Is Not the Entire Offboarding Process

Production offboarding also includes authorization, access revocation, data preservation, dependency review, and verification.

### 6. PowerShell Provides Auditable Administrative Workflows

Microsoft Graph and Active Directory PowerShell allow administrators to inspect identities, review permissions, disable access, and verify account state.

Commands should be documented alongside actual results.

### 7. Administrative Access Should Be Recoverable

Independent cloud-only administrator accounts reduce dependence on any single identity or on-premises directory.
