## 1. Incident Summary

A Sales employee reported that audio had stopped working on his Windows workstation.

The user could log into Windows normally but could not hear audio from Microsoft Edge, YouTube, or Windows system sounds.

Initial investigation revealed that the Windows Audio service (`Audiosrv`) was stopped and disabled on COMP01.

The service was restored through an elevated PowerShell session by changing its startup type to Automatic and starting it.

**Root cause:** Windows Audio service disabled on the affected endpoint.

**Resolution:** Reconfigured and started the Windows Audio service.

**Verification:** Both Windows audio services were confirmed running with Automatic startup. Physical audio playback was not independently verified.

## 4. Troubleshooting Approach

Windows audio issues can originate from several layers.

| Layer | Examples |
|---|---|
| Hardware | Speakers, monitor, cables, power |
| Windows configuration | Muted audio, wrong output device |
| Services | Windows Audio, Audio Endpoint Builder |
| Drivers | Missing, disabled, or malfunctioning audio device |
| Applications | Application-specific mute or output settings |
| Management policies | GPO or Intune configuration restrictions |

Because the endpoint was a VMware virtual machine, functional speaker testing could be limited by virtual hardware configuration.

The investigation focused initially on Windows services.

## 5. Investigation

### Step 1 — Inspect Windows Audio Services

Executed:

```powershell
Get-Service -Name Audiosrv,AudioEndpointBuilder |
    Select-Object Name, Status, StartType
```

The first investigation was accidentally performed in the domain controller's administrative PowerShell session rather than on COMP01.

Initial result on the DC:

```text
Name                  Status   StartType
----                  ------   ---------
AudioEndpointBuilder  Stopped  Manual
Audiosrv              Stopped  Manual
```

At first, these results appeared to explain the user's problem.

However, the command was executed locally on the DC.

**Important finding:** `Get-Service` without an explicit remote target checks the machine running the command.

The DC's service state was not evidence of COMP01's service state.

### Step 2 — Accidental Remediation on the DC

The following commands were executed on the DC:

```powershell
Set-Service -Name AudioEndpointBuilder -StartupType Automatic
Start-Service -Name AudioEndpointBuilder

Set-Service -Name Audiosrv -StartupType Automatic
Start-Service -Name Audiosrv
```

Both services subsequently reported:

```text
Running / Automatic
```

This was an unnecessary configuration change because the domain controller was not the affected workstation.

The DC's original observed state was:

| Service | Status | Startup Type |
|---|---|---|
| AudioEndpointBuilder | Stopped | Manual |
| Audiosrv | Stopped | Manual |

**Follow-up:** Restore the DC's original service configuration if not already completed.

### Step 3 — Inspect the User's Endpoint

Switched to John Smith's session on COMP01.

Checked the account context:

```powershell
whoami
```

Result:

```text
aden\jsmith
```

Attempted to inspect the services:

```powershell
Get-Service -Name Audiosvr,AudioEndpointBuilder |
    Select-Object Name,Status,StartType
```

This produced an error because `Audiosvr` was misspelled.

Correct service name:

```text
Audiosrv
```

Corrected the command:

```powershell
Get-Service -Name Audiosrv,AudioEndpointBuilder |
    Select-Object Name,Status,StartType
```

Result on COMP01:

```text
Name                  Status   StartType
----                  ------   ---------
AudioEndpointBuilder  Running  Automatic
Audiosrv              Stopped  Disabled
```

**Finding:** Windows Audio was disabled on COMP01.

This was consistent with the user's reported inability to hear audio.

## 6. Permissions and Administrative Access

### Attempted Remediation as John Smith

While using John's standard-user session, attempted:

```powershell
Set-Service Audiosrv -StartupType Automatic
Start-Service Audiosrv
```

PowerShell returned:

```text
Set-Service : Access is denied.
```

The subsequent attempt to start Windows Audio also failed.

### Why This Happened

Windows services are managed at the operating-system level.

Standard domain users generally cannot change protected service configurations.

Membership in the domain does not automatically grant local administrative privileges.

**Lesson:** The technician must use an appropriately authorized elevated administrative session to modify Windows services.

### Accounts and Privileges

| Account | Role in Incident |
|---|---|
| `aden\jsmith` | Affected end user; insufficient privileges to change service configuration |
| `aden\administrator` | Administrative account used for remediation |
| Local elevated PowerShell | Used to change service startup configuration and start services |

The technician subsequently opened an elevated administrative PowerShell session on COMP01.

### Step 1 — Confirm the Affected Service

Executed in elevated PowerShell:

```powershell
    Select-Object Name,Status,StartType
```

Observed:

```text
AudioEndpointBuilder  Running  Automatic
Audiosrv              Stopped  Disabled
```

### Step 2 — Change the Startup Type

Initially executed:

```powershell

```

Result:

```text

```

This successfully changed the startup configuration but did not start the service.

Then executed:

```powershell

```

Result:

```text
Audiosrv  Stopped  Automatic
```

The service remained stopped because `Set-Service` modifies configuration rather than starting the service.

```powershell

```

### Step 4 — Verify Service Status

Executed:

```powershell
Get-Service Audiosrv,AudioEndpointBuilder |
    Select-Object Name,Status,StartType
```

Final state reported:

```text
Name                  Status   StartType
----                  ------   ---------
AudioEndpointBuilder  Running  Automatic
Audiosrv              Running  Automatic
```

**Result:** The injected Windows Audio service fault was remediated.

## 8. Root Cause Analysis

### Technical Root Cause

The Windows Audio service (`Audiosrv`) on COMP01 had been disabled and stopped.

With the service disabled, Windows audio functionality was unavailable.

The Audio Endpoint Builder service remained running and configured for Automatic startup.

### Lab Context

The service configuration was intentionally modified as part of a simulated endpoint support ticket.

### Production Considerations

In a production environment, the technician should investigate why a service became disabled.

Potential causes include:

- Administrative configuration changes
- Endpoint management policies
- Software installation or removal
- Security or hardening configuration
- Service configuration corruption

These are general possibilities, not confirmed causes of this lab incident.

### Windows Service Administration

| Command | Purpose |
|---|---|

**Important distinction:**

- `Get-Service` reads the current state.
- `Set-Service` modifies service configuration.
- `Start-Service` starts a service.
- `Stop-Service` stops a service.
- `Restart-Service` restarts a service.

### PowerShell Remoting vs. Local Administration

| Method | Where the Command Executes |
|---|---|
| PowerShell opened on COMP01 | COMP01 |
| PowerShell opened on DC | DC |

| Remote Desktop session into COMP01 | COMP01 |

## 14. Lessons Learned

### Windows Endpoint Support

- Audio problems can originate from hardware, software, drivers, services, or endpoint configuration.
- Windows Audio (`Audiosrv`) is a critical component of Windows sound functionality.
- Audio Endpoint Builder supports audio endpoint management.
- Service configuration and service runtime state are different.

### PowerShell

- `Get-Service` checks the local computer by default.
- `Set-Service` changes configuration but does not necessarily start a service.
- `Start-Service` is needed to start a stopped service.
- `Select-Object` makes command output easier to read.
- Service names must be spelled correctly.

### Identity and Access

- Standard domain users generally cannot modify protected Windows services.
- Administrative actions require appropriate privileges.
- Running PowerShell as administrator differs from running it as a standard user.
- `whoami` identifies the current account, not the target computer.
- `hostname` identifies the computer.

### Troubleshooting Process

- Confirm the target machine before running administrative commands.
- Verify the affected service before making changes.
- Avoid unnecessary changes to unrelated infrastructure.
- Confirm remediation through a second diagnostic check.
- Distinguish service-level verification from end-user functionality.
