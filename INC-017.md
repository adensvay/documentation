
# INC-017 — Internal Resource Connectivity Failure (DNS A Record)

**Date:** October 15, 2026  
**Category:** Networking / DNS Troubleshooting  
**Priority:** P3 — Normal  
**Status:** Resolved — Lab Verification Successful  
**Environment:** Windows Server 2022, Windows 11, Active Directory DNS

---

## 1. Incident Summary

A user reported being unable to access an internal company resource, `portal.aden.local`, from their Windows 11 workstation.

The user stated that general internet connectivity was working normally, but the internal resource was unreachable.

The objective was to isolate the failure, identify its root cause, restore the correct DNS configuration, and verify network connectivity.

**Affected workstation:** `COMP01`  
**Affected resource:** `portal.aden.local`  
**Domain:** `aden.local`

> **Lab scope:** `portal.aden.local` is a simulated internal service alias pointing to the domain controller's DNS service. No actual web portal was deployed. Successful resolution was verified through DNS queries and TCP connectivity on port 53.

## 3. User-Reported Issue

The user reported:

> "I'm having trouble connecting to our internal company portal from COMP01. My internet connection seems fine, and I can access other websites, but the internal portal isn't responding."

The technician acknowledged the issue and began investigating from the affected workstation.

### Initial Hypotheses

Possible causes included:

- General network connectivity failure
- DNS resolution failure
- Incorrect DNS record
- Unreachable destination server
- Firewall or port connectivity issue
- Client-side network misconfiguration

The investigation focused on isolating the affected layer before modifying any configuration.

## 4. Establishing a Known-Good Baseline

Before the fault was introduced, the internal hostname was configured to resolve to the domain controller.

### DNS Resolution

```powershell
Resolve-DnsName portal.aden.local -Type A
```

Result:

```text
Name               Type   TTL   Section   IPAddress
----               ----   ---   -------   ---------
portal.aden.local  A      3600  Answer    192.168.17.128
```

### TCP Connectivity

```powershell

```

Result:

```text

RemoteAddress    : 192.168.17.128
RemotePort       : 53
InterfaceAlias   : Ethernet0
SourceAddress    : 192.168.17.129
TcpTestSucceeded : True
```

This confirmed that the client could resolve the hostname and establish a TCP connection to the expected endpoint.

## 5. Fault Injection

A controlled DNS misconfiguration was introduced on the domain controller.

The A record for `portal.aden.local` was changed from:

```text
192.168.17.128
```

To:

```text
203.0.113.77
```

The incorrect address belongs to `203.0.113.0/24`, a reserved documentation range (TEST-NET-3).

The original DNS record was backed up before modification.

### Confirming the Failure

On `COMP01`, the DNS client cache was cleared:

```powershell
Clear-DnsClientCache
```

The connection was tested again:

```powershell
Test-NetConnection portal.aden.local -Port 53
```

Observed output:

```text
WARNING: TCP connect to (203.0.113.77 : 53) failed

ComputerName     : portal.aden.local
RemoteAddress    : 203.0.113.77
RemotePort       : 53
InterfaceAlias   : Ethernet0
SourceAddress    : 192.168.17.129
PingSucceeded    : False
TcpTestSucceeded : False
```

The failure was successfully reproduced.

## 6. Troubleshooting and Investigation

### Step 1 — Verify External Network Connectivity

The technician tested connectivity to a known public IP address:

```powershell
ping 8.8.8.8
```

Observed result:

```text
Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)
Minimum = 3ms, Maximum = 5ms, Average = 4ms
```

**Finding:** External IP connectivity was operational.

This reduced the likelihood of a general network outage.

### Step 2 — Verify External DNS Resolution

```powershell
Resolve-DnsName -Name google.com
```

The command successfully returned multiple IPv4 and IPv6 addresses.

**Finding:** External DNS resolution was functioning.

The problem appeared isolated to the internal resource rather than general DNS availability.

### Step 3 — Investigate Internal DNS Resolution

```powershell
Resolve-DnsName -Name portal.aden.local
```

Observed result:

```text
Name               Type   TTL   Section   IPAddress
----               ----   ---   -------   ---------
portal.aden.local  A      3600  Answer    203.0.113.77
```

The hostname resolved successfully, but the returned address was unexpected.

**Finding:** DNS resolution was working, but the DNS record appeared to contain an incorrect destination.

### Step 4 — Test the Returned IP Address

```powershell
ping 203.0.113.77
```

Observed result:

```text
Packets: Sent = 4, Received = 0, Lost = 4 (100% loss)
```

**Finding:** The destination did not respond to ICMP echo requests.

A failed ping does not independently prove a server is offline because ICMP may be blocked by firewalls.

However, combined with the unexpected DNS address and failed TCP test, the results supported further investigation of the DNS record.

### Step 5 — Identify the Client's DNS Server

```powershell
Get-DnsClientServerAddress -AddressFamily IPv4
```

Observed result:

```text
InterfaceAlias   AddressFamily   ServerAddresses
--------------   -------------   ---------------
Ethernet0        IPv4            {192.168.17.128}
```

**Finding:** The client was configured to use the expected internal DNS server.

### Step 6 — Query DNS Directly

```powershell
nslookup portal.aden.local
```

Observed result:

```text
Server:  UnKnown
Address: 192.168.17.128

Name:    portal.aden.local
Address: 203.0.113.77
```

The DNS server at `192.168.17.128` returned the unexpected address.

The `UnKnown` server label does not necessarily indicate a DNS failure; it can occur when the DNS server's IP address lacks a corresponding reverse lookup record.

**Finding:** The internal DNS server was answering queries, but the hostname was mapped to the wrong IP address.

---

## 7. Root Cause

The authoritative DNS A record for `portal.aden.local` contained an incorrect IPv4 address.

| Setting | Expected | Faulty |
|---|---|---|
| Hostname | `portal.aden.local` | `portal.aden.local` |
| Record Type | A | A |
| IPv4 Address | `192.168.17.128` | `203.0.113.77` |
| TCP Port 53 | Reachable | Unreachable |

**Root cause:** Incorrect DNS A record.

The workstation was using the correct DNS server, but the hostname resolved to an unintended destination.

This was a DNS configuration issue, not a failure of the client's general internet connectivity or a change to its routing table.

---

## 8. Resolution

The technician corrected the DNS record using DNS Manager on the Windows Server 2022 domain controller.

### Procedure

1. Opened **Server Manager**.
2. Navigated to **Tools → DNS**.
3. Expanded **Forward Lookup Zones**.
4. Selected the `aden.local` zone.
5. Located the `portal` Host (A) record.
6. Opened the record properties.
7. Changed the IPv4 address from `203.0.113.77` to `192.168.17.128`.
8. Saved the updated DNS record.

The destination was restored to the previously verified lab endpoint.

### Clear Client DNS Cache

On `COMP01`:

```powershell
Clear-DnsClientCache
```

This removed cached DNS responses so the client could obtain the updated record.

## 11. Networking Concepts Reinforced

### DNS Resolution vs. Connectivity

A successful DNS lookup means a DNS server returned an answer.

It does not guarantee that:

- The returned IP address is correct.
- The destination server is online.
- The required TCP or UDP port is reachable.
- The application is functioning.

DNS resolution and service connectivity must be verified independently.

### DNS vs. Routing

DNS maps hostnames to IP addresses.

Routing determines how network packets travel toward their destinations.

Correcting an A record changes the address returned for a hostname. It does not change the destination server's actual IP address or the client's routing table.

### DNS Caching

DNS responses may be cached by clients, DNS resolvers, and other infrastructure.

After updating a DNS record, clearing the client DNS cache can help ensure subsequent tests use fresh resolution results.
